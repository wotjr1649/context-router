## 근거가 된 관측 (session-49, 2026-08-01)

v0.17.0의 `/code-review xhigh` 워크플로가 주간 한도로 끊겨 **verify 5건과 synthesis가 실행되지
않았다.** 그 후보 다섯을 재판정한 것이 이 문서의 출발점이다. 셋이 확정됐고 v0.17.1이 닫았으며,
둘은 현행 설계 계약이 그 동작을 명시하고 있어 v0.19로 갔다. 재판정 중에 session-48 §5.2가
**"판독으로만 확인했고 실행하지 않았다"**고 남긴 BOM 연쇄를 실측했고, 재현되어 v0.17.2가 닫았다.

두 패치가 닫은 것은 판정 라인 정규화와 보고였다. 남은 것이 v0.17이 "뿌리 A"라 부른 것 —
**판독기들이 같은 바이트를 서로 다르게 본다는 사실 자체** — 이고 이 릴리스가 그것을 닫는다.

### 관측 ① — 중첩 인라인에서 사용자 값을 조용히 덮어쓴다 (실측)

```
in   : env = { A = { CTR_MANAGED = "inner" }, B = "1" }
read : "inner"                    ← 안쪽 마디를 바깥 표식으로 읽는다
out  : 사용자의 A.CTR_MANAGED 값이 우리 표식으로 바뀐다
gate : 통과                       ← 산출이 유효 TOML이다
```

**이것이 D92의 가장 강한 근거다.** 게이트는 구문만 보므로 막지 못하고, doctor는 아무 말도
하지 않으며, 사용자는 자기 값이 바뀐 것을 알 수 없다. 현행 `tomlInlineValue`가 `{`·`,`에서
재개하는 형태라 깊이를 이월하지 못하는 것이 원인이다.

### 관측 ② — 점 표기 키가 깊이 1에 평평하게 놓인다 (실측)

```
in   : env = { CTR_MANAGED.sub = "x" }
read : found=false                ← 키 경계가 '.'에서 끊겨 못 찾는다
out  : env = { CTR_MANAGED = "…", CTR_MANAGED.sub = "x" }   ← 같은 키 두 번
gate : 거부 → 그 파일에서 install이 영구 무변경
```

TOML 명세가 `animal = { type.name = "pug" }`를 예제로 싣는다 — **점 표기 키는 중첩이 아니라
깊이 1 마디**다. 그러므로 "깊이 1만 열거한다"는 계약은 이것을 걸러 내지 못한다. v0.17 §3
표1 행3의 "판독 통일의 최악 회귀"가 깊이 1 열거형을 세워도 그대로 재현된다.

### 관측 ③ — 여러 줄 인라인 테이블은 줄어드는 예외가 아니다 (실측)

지정 파서(pelletier/go-toml v2)는 **중괄호로 이어진 여러 줄 인라인 테이블을 받는다**
(TOML 1.1.0이 인라인 테이블의 개행과 후행 쉼표를 허용했다). 그런데 `tomlLineScanner.advance`는
`[`·`]` 배열 균형만 세고 **`{`·`}`를 세지 않아** `codexEntries`가 그 형태를 한 엔트리로 묶지
않는다(실측: 두 엔트리로 갈라 잡는다). 열거형이 그 형태를 다루는 것은 선택이 아니다.

### 관측 ④ — 정규화가 주소 지정 대상을 파괴한다

`codexEntryText`는 물리 라인마다 `codexValueText = stripTrailingComment(stripLine(line))`을
적용해 잇는데 `stripLine`은 `strings.Fields`로 **따옴표 안 공백까지 지운다.** 그 산출은 어느
라인의 부분문자열도 아니므로 그 위에서 잡은 구간을 파일에 되쓸 수 없다. 같은 정규화가 v0.17
§1.2의 **잔여 ②**(`"e n v" = { … }`가 `env` 키로 읽혀 남의 테이블에 우리 표식이 서는 것,
실측 확인)의 원인이기도 하다.

> **그러므로 이 릴리스는 원시 하나를 세우고 소비자를 그 위로 옮긴다.** 되쓰기 신설은 넣지
> 않는다 — §0-D94-철회가 그 이유를 적는다.

한 가지를 함께 못박는다.

- **게이트(D89)는 이 릴리스의 백스톱이 아니다.** 관측 ①이 그 증거다: 사용자 값이 바뀌어도
  산출은 유효 TOML이고 게이트를 통과한다. **의미 보존은 §2가 감시선으로 잡는다.**

## 0. 결정 이력 (v0.18 신규 — D91까지는 이전 델타 체인)

### D92 — 인라인 판독 원시를 한 패스 열거형 하나로

**결정**: 인라인 테이블의 키·값 경계를 찾는 걸음을 **한 패스 열거형 하나**로 모으고, 소비자
넷이 그 하나를 지난다.

```go
// tomlPoint — 파일 좌표. 없으면 (-1, -1).
type tomlPoint struct{ line, col int }

// tomlSpan — [start, end) 반오픈. 두 지점 모두 파일 좌표.
type tomlSpan struct{ start, end tomlPoint }

type tomlInlineEntry struct {
    key     tomlSpan // 점 표기면 **경로 전체**의 구간
    value   tomlSpan
    segs    int      // 따옴표 밖 '.'로 가른 마디 수. 1이면 단순 키
    escaped bool     // 어느 마디든 역슬래시 이스케이프(D93 — 표시만)
}

type tomlInlineScan struct {
    open, close tomlPoint
    entries     []tomlInlineEntry
    ok          bool // false = 구조 미확정. 소비자는 각자 원문 보존으로 빠진다
    // braced — 그 ok=false를 **둘로 가른다**. false면 우변이 애초에 `{`로 열리지 않은 것이라
    // (`env = []`·`env = "x"`) 마디가 **있을 수 없고**, 그러므로 표식의 부재를 **아는** 것이다.
    // true면 열리기는 했는데 그 안을 확정하지 못한 것이라(`env = { A = }`) 표식이 그 안에
    // 있을 수도 있어 부재를 **모르는** 것이다. 판정원 하나가 자기가 본 것을 말하는 자리이며,
    // 이 구분이 없으면 "소유를 모르는 파일"과 "남의 파일"이 같은 값으로 내려온다(계약 7).
    braced bool
}

func tomlScanInline(lines [][]byte, e [2]int) tomlInlineScan
```

#### 왜 재개형이 아닌가

현행 `tomlInlineValue`·`inlineMarkerSpan`은 `{`·`,`를 만나면 거기서 키를 읽는 **재개형**이라
중첩 깊이를 이월하지 못한다 — 관측 ①이 그 귀결이다. 깊이를 각 자리에서 따로 세는 방향은 지금
갈린 것과 같은 실패를 자리 수만큼 재생산한다. 한 패스 열거형은 깊이를 **상태로** 들고 간다.

#### 계약 일곱

1. **깊이 1의 마디만 열거한다.** 중첩 인라인 테이블은 **값으로 통째** 잡힌다 — 관측 ①이 닫힌다.
   **이것만으로는 관측 ②가 닫히지 않는다**(점 표기 키는 깊이 1이다). 그 몫은 계약 3이 진다.
2. **잇는 것은 "물리 라인마다 주석만 잘라 낸 원문"이고, 공백 건너뛰기는 상태 기계가 한다.**
   정규화 산출 위에서 열거하지 않는다(관측 ④). 귀결 셋:
   - 되사상이 **라인당 한 항목**으로 줄어든다. 각 라인의 보존 구간이 `[0, 주석위치)`라는
     접두 슬라이스이므로 `joinedStart[i]` 하나면 `col = o - joinedStart[i]`다. CRLF·마지막 줄
     종결자 없음이 전부 접미 절단이라 자동으로 옳다.
   - **잔여 ②가 구성으로 닫힌다** — 따옴표 안 공백을 애초에 지우지 않으므로 `"e n v"`가
     `env`로 읽힐 수 없다(실측 확인). 그러므로 **엔트리 좌변 키를 읽는 자리도 이 원문 위로
     옮긴다**(`codexKeyName(codexEntryText(...))` — 소비자 5).
   - **문자열 밖 공백은 상태 기계만이 아니라 키 추출도 함께 무시한다.** 이 한 줄이 없으면
     전환이 조용히 깨진다: 현행 `codexKeyName`은 공백이 이미 지워진 입력을 전제하므로 원문
     위에서는 bare 키마다 **후행 공백이 붙은 이름**을 낸다(실측:
     `codexKeyName("env = { … }") = "env "`). 그러면 `codexReadTable`의 키 분기가 전부 미스하고
     `codexEnvBody`의 표식 줄 제외도 서지 않는다. 같은 규칙이 **이스케이프 키 검사**에도
     걸린다 — `tomlKeyTokenHasEscape`가 닫는 따옴표 **바로 뒤** `=`를 요구하므로 공백을
     건너뛰지 않으면 D87의 이탈이 fail-open으로 뒤집힌다(실측:
     `"C:\t" = 2` → false / `"C:\t"=2` → true). 규칙을 하나로 두면 두 자리가 함께 옳다.
   - 저장소에 선례가 있다: `tomlDottedEnvKey`가 D90에서 **정확히 같은 이유로** "입력은 정규화
     라인이 아니라 문자열 밖 공백만 무시한 원문 LHS다"를 결정했고 `tomlTopLevelEq` + 마디
     `TrimSpace`가 이미 그 형태다. 새 원칙이 아니라 그 선례의 확장이다.
3. **`segs`는 소비한다. `escaped`는 소비하지 않는다.** 성격이 다르다 — `escaped`를 읽으면
   무변경 집합이 넓어지고 기존 이스케이프 픽스처의 판정이 뒤집힌다(그것이 D93이다).
   `segs`는 읽지 않으면 관측 ②가 그대로 살아 있다.

   **소비 지점은 `setInlineEnvMarker`가 아니라 D90의 이탈 반환과 같은 자리**(소유 판정 뒤 ·
   `ownedSame` 무변경 반환 앞)다. `setInlineEnvMarker`는 라인 하나를 돌려줄 뿐 **상태도 사유도
   실을 수 없고**, 거기서 원문을 보존해도 `codexTableBody`가 나머지 관리 키를 계속 기입하므로
   재기준선 행 2가 요구하는 "무변경 + 사유 + 산출 바이트 동일"이 나오지 않는다.
   ```
   깊이 1 마디 중 첫 마디가 표식 키인 점 표기가 하나라도 있으면
   → 삽입은 중복 정의를 만든다. 표식으로 읽히지도 않았으므로 갱신 갈래도 설 수 없다
   → mcpMarkerAnomaly + 사유(anomalyDottedEnv 재사용 — 사용자가 볼 조치가 같다) + 무변경
   ```
   `tomlSplitDotted`가 이미 따옴표 밖 `.`에서 가른다. 새 함수는 없다.
4. **찾지 못한 지점은 `(-1, -1)`이고, 부분 산출을 내지 않는다.** 미종료 문자열·짝 없는 괄호·
   `close` 부재 어느 경우든 `ok=false`와 함께 `entries`를 **비워** 돌려준다. 절반만 열거된
   결과는 소비자 3에게 "비어 있다"로 보이고 그것이 곧 관측 ②의 산출이다. `0`을 무효로 쓰지
   않는 이유는 v0.17 §1.4-라가 마커 인덱스에 적은 것 그대로다.
5. **괄호는 단일 카운터가 아니라 스택이다.** 현행 `tomlInlineValueEnd`는 `]`와 `}`를 한
   `depth`로 세고 `]`에서 무조건 감소시켜 음수로 내려갈 수 있다. 새 원시는 그 형태를
   물려받지 않는다. **후행 쉼표에서 유령 엔트리를 내지 않는다** — `expectKey` 상태에서 `}`를
   만나면 정상 종료다(TOML 1.1.0이 허용하고 지정 파서가 받는다).
6. **주석 절단은 이월된 문자열 상태가 결정한다.** 현행 `stripTrailingComment`는 라인 단위
   무상태라 여러 줄 기본 문자열 안의 `#`을 주석으로 잘라 낸다. 열거형은 상태를 들고 있으므로
   공짜로 옳아진다.
7. **구조를 읽지 못했으면 소유는 "부재"가 아니라 "미상"이다.** 계약 4가 `ok=false`에서
   `entries`를 비우므로, 표식을 찾는 소비자는 **찾지 못했다**를 돌려받는다. 그 값을 소유
   판정이 "표식이 없다"로 읽으면 곧바로 "남의 테이블"이 되는데, 그것은 **근거 없는 주장**이다
   — 우리가 못 읽었을 뿐 표식은 그 중괄호 안에 있을 수 있다. 그래서 `braced`가 둘을 가르고,
   다른 소유 절이 하나도 서지 않은 상태에서 `braced && !ok`이면 **소유 미상**으로 내려
   `mcpMarkerAnomaly` + 사유로 보고한다.

   **왜 이것이 계약인가**: 미상을 "남의 것"으로 보고하면 `uninstall`이 남의 등록물을 건드리지
   않는 규칙에 걸려 아무것도 지우지 않고 **exit 0에 "제거 완료" 문면**을 낸다 — 사용자의
   `config.toml`에는 우리 서버가 그대로 등록돼 있는데 성공만 보인다. 미상으로 내리면 같은
   자리가 "형태를 고치고 재실행하라"는 수행 가능한 사유를 낸다. 여전히 지우지는 않지만,
   **틀린 성공 대신 옳은 보류**다.

   이탈의 자리는 **소유 판정의 부정 갈래 안**이다. 기존 `anomalyEnvNotTable` 게이트(소유 판정
   **뒤**)를 위로 옮기면 두 사유의 우선순위가 바뀌어 둘을 함께 담은 입력에서 문면이 뒤집힌다.

상태 기계의 형태: `expectKey → inKey → expectEq → expectValue → inValue → expectSep → …`,
괄호 스택, 한 줄 문자열은 `basicStringLen`/`literalStringLen` 재사용, 여러 줄 `"""`·`'''`
열림은 `tomlLineScanner`와 같은 걸음으로 이월.

#### 입력의 경계 — `codexEntries`가 `{`·`}`를 세야 한다

열거형의 입력은 **논리 엔트리**인데, 관측 ③대로 `tomlLineScanner`가 `{`·`}`를 세지 않아
여러 줄 인라인 테이블이 한 엔트리로 묶이지 않는다. 그러므로 **스캐너의 상태에 인라인 깊이를
더하는 것이 이 릴리스의 배송 항목이다**(§1.1 행 1).

- 그 확장은 `sc.open()`을 통해 **테이블 경계 판정에도** 걸린다. 닫히지 않은 `{`가 있으면
  뒤따르는 헤더가 값 안으로 들어가는데, 그 입력은 이미 무효 TOML이고 기존
  `anomalyScannerOpen`이 받는 상태와 같은 부류다 — **사유 문면에 인라인 테이블을 더한다**
  (현재 문면은 "여러 줄 문자열 또는 배열"만 말한다).
  - **EOF 백스톱만으로는 그 부류가 잡히지 않는다(session-54 실측 정정).** 삼켜진 헤더 자신의
    대괄호가 깊이를 도로 맞추므로 스캐너는 EOF에서 닫힌 채 끝나고, 사유 없이 `changed=true`로
    빠져나간다 — 따옴표 넷 갈래(§0 감사 기록)가 같은 기제로 물렸던 그 자리이며, 거기서는
    닫기 규칙을 고쳐 헤더가 다시 경계가 되게 했지만 이 갈래는 그럴 수 없다. 잡는 것은
    **"인라인 테이블이 열린 채 헤더 모양의 줄이 온다"**는 규칙이다. 좁힘의 근거는 TOML이
    인라인 테이블 안의 줄바꿈을 **값 안에서만** 허용한다는 것 — 열린 배열이나 여러 줄 문자열이
    있으면(`args = [`⏎`["nested"],`⏎`]` · 인라인 안의 중첩 배열 · 문자열 내용 줄) 그 줄은
    정상이므로 규칙이 들지 않는다. 술어는 `열린 괄호가 전부 중괄호 && 문자열 밖`이다.

**행 15~16은 태그 전 리뷰의 마지막 결함 셋을 판정하며 움직인 것이다**(session-55). 셋 중

- **행 15는 고치지 않았다 — 새 판정이 옳다.** 소유는 D84의 **세 절 disjunction**이고 첫 절이
  "`env.CTR_MANAGED` 값이 소유 기준을 만족"(D82)이다. `command` 절은 그것과 **또는**으로 묶이
  므로 남의 `command`는 첫 절의 반증이 아니다. 따옴표 표기 `"CTR_MANAGED"`는 TOML이 bare 키와
  **같은 키**로 읽으므로 그 파일에 표식은 실재한다. **결정적 실측은 base 자신이다**: 같은
  파일에서 표식을 엔트리 **첫 물리 라인**으로 옮기면 base도 `mcpWritten`·기입·`uninstall`
  제거를 낸다(`command = "other"` 그대로). 즉 base의 두 판정을 가른 것은 계약이 아니라
  **판독기의 물리 라인 한정**이고, 그것이 소비자 표 행 1·2와 관측 ③이 고치라고 지목한 결함
  그 자체다 — 표식이 앉은 물리 라인은 소유 절 어디에도 없다. 빠져 있던 것은 판정이 아니라
  이 표의 행이다(`TestCodexMarkerOwnsRegardlessOfPhysicalLine`이 두 자리의 **같음**을 잠근다).
- **행 16이 픽스다.** 점 표기 표식 키 차단이 **인라인 갈래에만** 배선돼 있었고, 헤더 형태는
  게이트에 닿지 못해 `mcpOutputInvalid`로 굳었다 — 그런데 그것이 **우리 설치기 자신이 기입하는
  형태**다. 사용자는 "제품 결함이니 알려 주세요"를 듣고 할 일이 없으며 install은 영구 무변경
  이다. 뿌리는 `codexEnvBody`가 표식을 **무조건** 내보내면서 그 건너뛰기는 이름이 **정확히**
  표식 키인 엔트리만 빼는 것이다 — 점 표기 스펠링은 남아 산출이 같은 논리 경로를 문자열과
  테이블로 두 번 정의한다. 두 형태를 술어 하나(`codexDottedMarkerBlocked`)가 답하게 하고,
  이탈을 **첫 기입 갈래 앞**에 세웠다: 관리 테이블 없이 헤더만 있는 파일도 그 갈래에서 같은
  산출을 내므로 뒤에 두면 그 형태만 옛 문면으로 남는다.

**판정을 움직이지 않은 픽스 하나 — 사유 문면이 자기 분류를 부정했다.** `anomalyEnvNotTable`의
문면은 "env 값이 인라인 테이블이 아니다"만 말했는데, 그 사유에 닿는 입력의 **한 부류 전체**가
중괄호로 열린 파일이다: 계약 7의 소유 미상(`codexMarkerUnknown`은 `braced && !ok`에서만 참이라
그 갈래의 파일은 **언제나** 중괄호로 열려 있다)과, 중괄호 안 구조를 확정하지 못한 게이트
갈래(쉼표 둘·빈 키·빈 값·짝 어긋난 괄호)다. `hook uninstall --codex`가 exit 0으로 그 안내를
내면 사용자는 파일을 열어 이미 `env = { … }` 형태인 것을 보고 아무것도 고치지 않은 채 제거가
끝난 줄 알고, 우리 테이블은 남아 Codex가 서버를 계속 띄운다(실측). 문면을 두 부류에 **모두
참인** 형태로 넓혔다 — `anomalyScannerOpen`("파일 끝 또는 다음 테이블 헤더 앞")과
`anomalyDottedEnv`가 이미 같은 이유로 넓힌 선례다. `State`·`Anomaly`·`Changed`·산출 바이트가
전후로 같으므로 **표에 행이 서지 않는다.** `anomalyDottedEnv`의 진단 절도 행 16의 셋째 형태를
담도록 함께 넓혔다 — 같은 이유이고 같은 무판정 변경이다
(`TestEnvNotTableReasonCoversBothClasses` · `TestDottedEnvReasonNamesEveryShape`).

**행 15~16에서도 격자는 5120·3072 그대로다**(실측). 행 15는 격자가 이미 기입 갈래로 세던

**표가 일곱 행이던 때 여덟째 행이 있었고, 태그 직전에 지웠다(감사 기록 — 위의 행 8~12와는

것을 실측으로 찾아 여덟째 행으로 실었고, 픽스를 v0.19로 미룬다고 적었다. **그 미룸을
철회하고 이 릴리스에서 고쳤다** — 판정이 base와 같아졌으므로 표에 남길 행이 없다.

- **뿌리는 탐욕적 닫기였다.** TOML의 실제 규칙은 **뒤에 같은 따옴표가 더 붙지 않은 첫 삼중
  따옴표**가 닫는다는 것이다(큰따옴표 넷은 내용이 따옴표 하나인 8바이트 토큰, 다섯이면

  않고 우리 구간이 EOF까지 늘어나는데, 그 뒤의 짝 없는 중괄호가 깊이를 도로 0으로 내려

- **blast radius를 다시 열지 않는다는 것도 실측했다.** 새 규칙과 옛 규칙은 **같은 따옴표가

  자로 만든 길이 6까지의 전수 대조(스캐너 시작 상태 여섯 겹)에서 비교 4185090건 · 갈림
  304건 · **실행 넷 없는 갈림 0건**이다. 격자 5120도 그대로 초록이고 기존 단정은 하나도

행 4의 변화폭이 넓은 이유: `codexKeyName`이 `env`를 읽어 `view.inlineEnv`가 서므로 지금은

**행 5~7은 구현 중에 더했다**(session-51, 소유자 판정). 넷만 적었을 때 빠져 있었고, 셋 다

  닫히지 않는 그 픽스처는 이미 무효 TOML이고, 사유를 내는 쪽이 옳다.
- **행 6·7은 소비자 표 행 1·2가 고치라고 지목한 결함 그 자체다.** 행 2가 "물리 라인 한정이라
  여러 줄 엔트리를 되쓰지 못한다"고 적은 것이 행 6이고, 행 1의 "판독기가 같은 바이트를 다르게

  `tomlInlineValue`는 문자열 토큰을 건너뛰지 않아 값 안의 `, CTR_MANAGED = …`를 키로 읽고,

  부재로 바로 읽고, 삽입이 사용자 값을 건드리지 않는다(실측: 산출 유효·멱등).

### D94(점 표기 파일의 헤더 형태 자동 이전) — 세웠다가 철회한다

이 세션 초반에 "표식이 옛 버전인 점 표기 파일에서 우리가 헤더 형태로 자동 이전한다"를 D94로
세웠다. **전제가 실측으로 무너져 철회한다.**

**세웠던 근거**: "Codex가 서버를 추가하며 재직렬화할 때 단일 키 `[mcp_servers.ctr.env]`를
`env.CTR_MANAGED = "…"`로 접으므로 **버전을 올릴 때마다** 사용자가 손편집을 해야 한다"
(v0.17 D90의 서술).

**실측**(Codex CLI 0.146.0 · Windows · 임시 `CODEX_HOME` · §3 표2):

- `codex mcp add`는 **재직렬화를 한다** — 주석 전부·미지 키·`args = []`가 사라진다.
  v0.15 §3 표1이 그대로 재현된다.
- 그러나 **`env`는 서브테이블 헤더로 되돌아온다. 점 표기가 아니다.** `mcp add` · `add`+`remove` ·
  `add --env` · `-c` nested 덮어쓰기 · 빈 파일에 `add --env`(Codex가 **새로 쓰는** 형태)
  **다섯 경로 전부** 헤더다.
- v0.15 §3 표1의 0.146.0 게이트 실측도 같은 것을 이미 기록하고 있다 — "`env`는 서브테이블
  헤더로 되쓰인다(인라인 대입 아님)". **v0.17 D90의 "접는다"에는 실측 인용이 없다.**

**귀결**: 접기가 없으면 treadmill이 없다. 점 표기는 손편집·구버전·타 도구가 만드는 **드문
일회성 상태**이지 정상 사용으로 도달하는 상태가 아니다. 그러므로 **D90의 무변경 이탈 + 수행
가능한 안내를 그대로 둔다.**

**함께 정정되는 것**: v0.17 D90의 "**정상 설치 뒤 정상 사용으로 도달하는 상태다**"와 session-48
§5.2의 같은 서술은 실측과 어긋난다. D90이 **점 표기를 읽는 것 자체는 옳다** — 유효 TOML이고,
그 형태를 못 읽으면 헤더를 덧붙여 사용자 파일을 깨며, v0.17이 재현한 파괴적 조치 넷은 그
상태를 구성해서 잰 것이라 작성자가 누구든 성립한다. 무너진 것은 **도달 빈도**뿐이다.

**철회로 함께 사라지는 위험**(자동 이전을 넣었다면 새로 들였을 것):

- 이전된 파일에서 **옛 바이너리는 깨뜨리지 않고 성공하며** 등록물을 옛 프로필로 되쓴다 —
  시끄러운 파손을 조용한 다운그레이드와 맞바꾸는 것이고, D91이 방금 세운 "도구 목록 부족"
  감지가 그 경로로 다시 들어온다.
- 상대의 재접기와 우리의 재펴기가 **형태 왕복**을 만들어 매 install이 바이트를 바꾸고,
  D84의 단일 백업 슬롯이 원본 대신 "직전에 우리가 고친 것"으로 채워진다.
- 잠금이 없는 파일에 기입자가 둘이라 **lost update**가 가능하고, VCS로 추적하는 사용자에게는
  워킹 트리가 계속 더러워진다.
- 우리가 소유하지 않은 줄(사용자가 손으로 적은 `env.FOO`)의 스타일을 바꾸게 되고, **주석
  귀속**(앞줄 독립 주석이 함께 옮겨지는가)이 정의되지 않는다.

**재개 조건**: **어느 경로든 접기가 반복 관측되는 것.** 가장 가까운 후보는 Codex TUI 자신의
config 기입(`/hooks` 신뢰 승인 등)이며 대화형이라 재지 못했다. 조건을 "TUI"로 좁히지 않는
이유는 위 귀결 문단이 점 표기 생산자로 손편집·구버전·**타 도구**를 함께 들기 때문이다 —
타 도구가 반복해 접는 관측도 같은 무게를 갖는다. **일회성 관측은 조건이 아니다**: 손편집 한
번은 자동 되쓰기를 정당화하지 않는다.

### D95(`.mcp.json`의 백업) — 세웠다가 이 릴리스에서 뺀다

**관측**: `config.toml`은 `backupCodexConfig`를 지나는데 `.mcp.json`은 `atomicWriteFile` 직접
덮어쓰기다. v0.17.1이 실행 전 예고를 `--fix`의 기입 조건과 묶었으나 **실행 후 복구 수단이
없다.** v0.16 스펙 §1.2가 D84 개정을 요구한 항목이다.

**세웠던 결정**: D84의 단일 백업 슬롯 계약을 `.mcp.json`에 같은 형태로 확장한다 — 기입이
실제로 일어나는 반환에서만 백업하고 슬롯은 하나(`.mcp.json.bak`)다.

**뺀다 — 슬롯의 자리가 정해지지 않았고, 그 자리가 자격증명 노출 경로다.** 아래 "뺀 이유"가
그 사실을 릴리스 안에서 이미 "알려진 한계"로 적고 있었고, 태그 직전 최대 노력 리뷰가 낸 결함
열다섯 중 **넷이 D95의 것**이었으며 그중 하나가 이 노출 경로다. 계약(단일 슬롯 · 기입한
반환에서만 · `uninstall` 비대상)은 옳다. 틀린 것은 **자리**뿐이며, 자리를 정하는 것은 릴리스
픽스가 아니라 설계 결정이다(§4). **관측은 유효한 채로 남는다** — `.mcp.json`에는 여전히
실행 후 복구 수단이 없다.

**대신 배송된 것 — install 자리의 바이트 비교.** 아래 선행 조건 절이 그것을 요구했고, 그
자체로 옳아 백업 없이도 남긴다: 종전 `hook install`은 `mergeMCPServers`의 `changed`를 버리고
**실행마다 무조건** 되썼다. 지금은 바이트가 다를 때만 쓰고 2회차 install이 진짜 무동작이다.
**릴리스 전 동작보다 엄격히 낫다** — 그쪽은 무조건 기입이면서 백업도 없었다. 무변경 갈래의
문면과, 등록이 확정된 **두 갈래를 함께 지나는** 빈 프로필 안내도 그 비교 위에 서 있다.

#### 선행 조건 — 기입 자리가 셋이고 바이트 비교는 한 자리뿐이다

| 자리 | 무변경 판정 | 백업을 그냥 걸면 |
|---|---|---|
| `doctor --fix` | `bytes.Equal(data, merged)` | 안전 |
| `hook install` | **없음** — `mergeMCPServers`의 `changed`를 버리고 무조건 쓴다(그 함수는 install에서 `changed`를 참으로 고정한다) | **2회차 install이 `.bak`을 설치 후 내용으로 덮어 원본을 잃는다** |
| `hook uninstall` | `changed` = 우리 항목이나 은퇴 항목을 **실제로 지웠는가** — 바이트 비교가 아니다 | 삭제는 언제나 바이트를 바꾸므로 헛 소모는 없다. 다만 판정이 **항목 존재**라, 재직렬화가 남의 서식까지 바꾸는 기입에도 슬롯이 소모된다 |

> **그러므로 install 자리에 바이트 비교를 세우는 것이 백업의 선행 조건이다.** 단일 슬롯은
> "2회차가 무변경"이라는 전제 위에 서 있고(D84), 그 전제가 세 자리 중 한 자리에서만 성립한다.

세 자리에 대해 세웠던 계약 셋은 **자리가 정해지면 그대로 다시 선다** — 백업 실패는 기입하지
않고 사유를 낸다(`config.toml` 갈래와 같은 순서) · `hook uninstall`은 백업 대상이 아니다(제거는
되돌릴 대상이 아니라 되돌림 자체다) · 기입한 실행의 문면이 슬롯 이름을 댄다(이름을 모르는
복구 수단은 복구 수단이 아니다).

#### 뺀 이유 — 슬롯이 버전 관리 안에 떨어진다

`config.toml`의 형제 슬롯은 `~/.codex/`에 있지만 **`.mcp.json`은 프로젝트 루트에 있다.**
그래서 `.mcp.json.bak`이 `git status`에 뜨고, `git add -A` 한 번이면 그 프로젝트의 MCP 설정
사본이 — 거기 실린 `env` 값까지 함께 — 공유 저장소에 커밋된다. **MCP 설정의 `env` 블록에
자격증명이 실리는 것은 흔하다**: 이 저장소가 자기 `.mcp.json`을 무시 목록에 둔 이유가 그것이고,
`.bak`은 대개 어느 저장소에도 규칙이 없는 이름이다.

배송본의 완화책은 **권고 문면 하나**였고 그마저 파일을 쓴 **뒤에** 인쇄된다 — 바이트가 이미
디스크에 있는 시점의 안내는 노출 경로를 닫지 못한다. 자기 저장소에 `.gitignore` 한 줄을 더한
것도 우리 저장소를 닫을 뿐 사용자 저장소에는 닿지 않는다.

**그래서 이 릴리스는 `.mcp.json`을 백업하지 않는다.** 자리를 옮기는 것은 릴리스 픽스가 아니라
설계 결정이다 — 경로가 바뀌면 무변경 판정·단일 슬롯·`uninstall` 비대상 세 계약이 함께 새 경로
위에서 다시 서야 하고, "설정 파일 옆"이라는 D84의 대칭을 깨므로 `config.toml` 갈래까지 함께
판단해야 한다. **후보와 함께 §4로 간다.**

`config.toml`의 백업은 그대로다 — D84로 이 릴리스 이전부터 있었고, 그쪽 슬롯은 `~/.codex/`라
같은 노출 경로가 없다. `backupConfigFile`은 그 파일 전용으로 남으며, 대칭으로 오해해 다시
붙이지 않도록 사유를 그 함수 주석에 적었다.

| 7 | 재기준선 열여섯 + §2의 감시선 다섯 겹 | 테스트 전체 |

행 5의 대상이 `codex_toml.go` 하나인 이유: 사유를 인쇄하는 **네 자리**(`[16]` · `[20]` ·
`hook install` 보고 · `hook uninstall` 보고)가 모두 `anomaly.reason()`을 값을 가리지 않고
**일반적으로** 지나므로 새 사유값 하나면 문면이 함께 따라온다.

### 1.3 게이트 — 선행과 사후

#### 선행(구현 시작 전에 판정한다)

1. **되사상의 정확성** — §2의 조합 격자(모든 줄 종결자 조합 · 선두 BOM 유무 · 들여쓰기 유무)
   에서 왕복(구간 → 원문 바이트 추출)이 항상 일치한다. **판정**: 저장소 밖 격리 모듈.

   > **이 게이트가 구조적으로 못 보는 클래스가 하나 있다 — 믿고 넘기지 마라(session-52 실측).**
   > 구간의 **배타적 끝**이 조각 경계 `at[k]`에 정확히 놓이면 그 오프셋에는 뜻이 둘이다:
   > "조각 k의 첫 바이트"와 "조각 k-1의 마지막 바이트 바로 뒤". 되쓰기가 옳으려면 **뒤엣것**
   > 이어야 하는데(앞엣것으로 풀면 그 사이 물리 라인이 통째로 치환 구간에 들어가 사용자의
   > 주석 줄·빈 줄이 사라진다), **두 해석이 `at[k]+col`로 같은 오프셋에 돌아오므로 어떤 왕복
   > 오라클도 둘을 가르지 못한다.** 같은 이유로 타일링(게이트 2 · P0)도 눈이 없다 — 그
   > 오라클도 되사상 뒤의 오프셋만 본다. 실제로 그 손실은 다섯 겹과 두 선행 게이트를 모두
   > 통과해 배송됐고, 나중에 `TestCodexInlineMarkerEndOnFragmentBoundary`(엔트리 바이트 동일)와
   > `TestCodexValueEndOnFragmentBoundaryOracles`(다섯 겹)가 픽스처로 잡았다.
   >
   > **격자에는 축을 더하지 않는다** — 케이스 수가 바뀌면 폭 고정 단정(5120)이 무의미해진다.
   > 이 클래스에 닿으려면 값 토큰이 줄 끝에서 끝나고 **다음 물리 라인이 쉼표로 시작**해야
   > 하는데 격자의 여러 줄 인라인 축은 쉼표를 앞줄 끝에 두므로, 5120 케이스 전부가 이 모양을
   > 만들 수 없다. `TestCodexInTableCommentsPreserved`가 같은 이유로 같은 선택을 한 선례다.
   >
   > **같은 부류의 자백 하나 더 — P3의 다중집합에는 출처가 없다(리뷰 실측).** 그 겹은 줄의
   > **개수**만 세고 살아남은 사본이 **어디서 왔는지**는 세지 않으므로, 우리가 재생성하는 줄과
   > 바이트 동일한 보존 라인은 **우리 자신의 산출**로 충족될 수 있다. 재현 형태: 남의
   > `[mcp_servers.other]` 안에 있는 `command = "context-router"` 줄이 사라져도 통과한다 —
   > 우리 관리 테이블이 같은 바이트의 줄을 내놓기 때문이다. 고치려면 개수가 아니라 출처를
   > 추적해야 하므로 이 릴리스는 고치지 않고 한계로 적는다.

2. **타일링** — 열거 결과가 논리 엔트리 바이트를 빈틈·겹침 없이 덮는다(§2.1 P0).

#### 사후(구현 뒤에 판정한다)

3. **순수성 유지** — 열거형과 그 호출 트리에 파일 IO·시간·난수가 없다(D85).
4. **판정 불변** — §0의 **재기준선 열여섯 밖에서** 기존 픽스처의 판정이 전후로 같다. 게이트가
   오탐하지 않게 하려면 의도 여부와 무관하게 **아는 뒤집힘을 전부** 적어야 한다 — 한때
   여덟째 행이 있었고, 그 뒤집힘은 미루는 대신 고쳐서 지웠다(§0 감사 기록). 태그 직전 픽스
   물결이 다섯을 더 움직였고 그것이 행 8~12다: **표를 "전부"라고 인용하는 이 게이트가
   실제로는 일곱만 담고 있었다** — 표를 늘리는 것이 게이트를 지키는 방법이다.
   행 15는 그 교훈이 한 번 더 걸린 자리다: 판정이 옳게 뒤집혔는데 **행이 없어서** 이 게이트가
   그것을 회귀로 보이게 했다. 새 판정이 계약의 귀결이면 고칠 것은 코드가 아니라 표다.
5. **오발화 없음** — install·uninstall 기존 픽스처의 산출물이 전부 게이트를 통과한다.

## 2. 검증·테스트 계약

### 2.1 다섯 겹 — 무엇이 무엇을 못 보는지에서 나온다

| 오라클 | 잡는 것 | 놓치는 것 |
|---|---|---|
| 게이트(구문) | 무효 TOML | 값 소실·주석 소실·값 변조 |
| 파서 맵 비교 | 값 소실·변조·이동·타입 변화 | **주석 전부**(파서가 버린다) · 키 순서 · 표기 |
| 골든 파일 | 형식까지 전부 | 픽스처 밖 전부 |

**P0 — 열거형 타일링.** 열거 결과가 논리 엔트리를 **구조 문자만 사이에 두고** 덮어야 한다:
구간과 구간 **사이**의 바이트가 그 자리에 올 수 있는 구조 문자(공백 · `=` 정확히 하나 ·
엔트리 사이 `,` 정확히 하나 · 마지막 값과 닫는 중괄호 사이 `,` 0개나 1개)뿐이고, 구간 자체는
비지 않으며 공백·`,`·`=`로 시작하거나 끝나지 않는다. rowan의 "자식 폭의 합 = 부모 폭"을 이
문법에 옮긴 형태다. 오프셋 ±1, 반오픈/닫힌 혼동, CRLF 되사상 오류, 후행 쉼표 유령 엔트리를
전부 문다 — 키 이름 비교로는 잡히지 않는 축이다.

> **"구간을 잘라 사이 바이트와 함께 다시 이으면 입력과 바이트 동일"로 적으면 안 된다.**
> `joined[prev:s] + joined[s:x] == joined[prev:x]`이므로 그 재구성은 **어떤 구간 열에 대해서도
> 항상 참**인 동어반복이고, 의도적 오프셋 ±1을 하나도 물지 않는다(session-49 리허설 실측:
> 돌연변이 아홉 종 × 픽스처 여덟에서 검출 0건). 무는 것은 위의 "사이 바이트가 구조 문자뿐"
> 쪽이다(같은 실측에서 아홉 종 전부 검출).

**P1 — 차집합 의미 오라클.** 헤더·점 표기·인라인 세 형태가 **같은 경로로 접히도록** 평탄화한
뒤 입력과 산출의 차집합이 허용 경로 안에 드는지 본다. 지정 파서는 **우리 판독기가 아닌 독립
구현**이라 차등 오라클로서 정당하고, D89가 검증 전용 사용을 이미 허용한다. 입력이 파스되지
않으면 건너뛴다 — D89의 비대칭 계약과 같은 형태다.

**P2 — 주석 다중집합.** 문자열 밖 `#`부터 줄 끝까지를 모아 정렬 비교한다. P1이 구조적으로 못
보는 축을 덮고, **파서를 쓰지 않으므로** 게이트와 오라클이 같은 파서라 맹점이 동시에 꺼지는
함정도 함께 해소된다. **문자열 상태는 줄 머리가 아니라 줄 안에서 본다** — `codexEntryRaw`와
같은 기준이고, 같은 기제(`tomlLineScanner.advance`가 내는 문자열 밖 `#` 자리)를 쓴다.
줄 머리 상태로 판정하면 여러 줄 문자열이 **닫히는 그 물리 라인**이 통째로 빠진다(아래 구멍 C).

**P3 — 원문 라인 생존.** 우리 관리 키가 아닌 물리 라인은 산출에 **바이트 동일**하게 있어야
한다. P1이 통과시키는 표기 변화(`1_000`→`1000`, `'x'`→`"x"`, 들여쓰기·후행 주석 소실)를
여기서 잡는다. **예외는 인라인 `env` 논리 엔트리 하나다** — 그 엔트리는 보존 라인이면서
표식이 제자리 치환되는 유일한 자리이므로(`codexTableBody`의 keep 루프가 `view.inlineEnv`에서만
`setInlineEnvMarker`를 지난다). Task 6 이후 그 엔트리는 여러 줄일 수 있으므로 예외는 라인
하나가 아니라 구간이다. 예외를 적지 않으면 그 엔트리 때문에 P3가 항상 실패하거나, 반대로
P3를 느슨하게 만들어 다른 줄의 변조까지 통과시킨다.

**예외의 폭은 "엔트리 전체 면제"다 — 그것이 계약이다.** 종전 문면은 예외 안에서도
**"치환 구간 밖 바이트 동일"**(엄격형)을 요구했으나 구현은 엔트리 전체를 면제한다. 이
어긋남은 **문서상의 것이고 살아 있는 구멍이 아니다**: 리뷰어가 엄격형
(`outEntry == raw[:spanStart] + repl + raw[spanEnd:]`)을 실제로 구현해 적대적 코퍼스 전체에
돌린 결과 **느슨한 규칙이 통과하는 모든 자리에서 함께 통과했다** — 엄격형이 더 잡는 것이
없다. 유일한 실제 누출이 파일 좌표상 치환 구간 **안**에 있기 때문이다(아래).

**다만 면제는 엔트리가 삼킨 첫 테이블 헤더 앞에서 끊는다**(session-53 개정, 아래 구멍 B).
면제의 근거는 "표식 splice가 이 엔트리 안을 정당하게 되쓴다"인데, **테이블 헤더 줄을 담은
엔트리는 정당한 엔트리가 아니다** — 판독기가 인라인 테이블을 닫지 못해 그 뒤 사용자 테이블을
엔트리 안으로 끌어들인 상태이고, 그 상태에서 종전 폭은 사용자 라인까지 면제했다. 같은 이유로
**구간 안 헤더 면제도 우리 이름의 헤더에만 준다**: 우리 구간은 그 상태에서 EOF까지 늘어나므로
"구간 안에서 `[`로 시작하는 줄"이라는 종전 판정은 남의 `[other]` 헤더까지 재생성 대상으로
면제했다. 헤더 판정은 `codexManagedSpans`가 쓰는 자리 그대로다(`stripLine` 뒤 `tomlHeaderName`) —
갈리면 오라클과 판독기가 같은 파일을 두 기준으로 읽는다.

> **예외 안의 예외 — 표식 값 구간 안의 주석은 사라진다(D88과 같은 부류).**
> `env = { CTR_MANAGED = [1, # note` 다음 줄 `2] }`에서 `# note`는 산출에 남지 않는다.
> 기제: `codexEntryRaw`가 물리 라인마다 주석을 잘라 `joined`를 만들므로 joined 공간에서
> 연속인 값 구간이 **파일 공간에서는 연속이 아니고**, `spliceInlineSpan`이 그 사이의 잘린
> 주석까지 함께 먹는다. **관리 키(`CTR_MANAGED`)의 값에 붙은 주석**이므로 D88이 이미 보존
> 대상에서 뺀 것과 같은 부류이고, 그래서 **고치지 않는다**(소유자 판정, session-52). 값 구간
> **밖**의 주석 — 앞줄 독립 주석 · 엔트리 뒤 후행 주석 — 은 그대로 남는다.
> `codex_toml.go` 파일 머리 주석의 D88 항이 같은 내용을 코드 쪽에 적는다.
>
> **그 폭을 못박는 것은 `TestCodexInlineValueSpanCommentIsRemoved`가 아니다(정정).** 종전
> 문면은 그 픽스처가 "손실이 넓어지는 회귀"를 문다고 적었는데, **실제로 넓어진 회귀가 있었고
> 그 픽스처는 내내 초록이었다** — session-52 실측: 회귀 상태(`071fdc9`)에서 그 테스트도,
> 격자 5120 케이스도, `TestCodexInTableCommentsPreserved`도 전부 PASS다. 그 픽스처의 값 구간은
> 조각 경계에 닿지 않아 손실 경로를 지나지 않으므로, 자기 형태 하나를 고정할 뿐 폭의 상한이
> 아니다. 폭을 실제로 무는 것은 §1.3 선행 게이트 1의 인용문이 든 두 픽스처
> (`TestCodexInlineMarkerEndOnFragmentBoundary` · `TestCodexValueEndOnFragmentBoundaryOracles`)다.

**P4 — 멱등.** 이 릴리스가 더하는 모든 픽스처에 `install(install(x)) == install(x)`. D84의
단일 슬롯과 `.mcp.json` 기입 자리의 바이트 비교가 그 전제 위에 서 있다.

#### 그물 자신의 구멍 넷 — session-53에서 재고 뒤 수리했다

max-effort 릴리스 리뷰 **둘**이 파일 파괴 결함을 냈는데 **그때 그물은 초록이었다.** 리뷰가
밝힌 그 이유 넷을 여기 적는다. 위 §1.3의 자백 둘(왕복 오라클의 맹점 · P3 다중집합의 출처
없음)과 **다른 항목**이고, 그중 하나(D)는 자백 목록에 오르지도 않았던 종류다 — 그물이
**오경보를 내서** 형태 하나를 통째로 검증 밖으로 밀어낸 경우다.

**A — 격자 5120 중 2048이 아무것도 검증하지 않았다.** 기입 갈래를 탄 것은 3072뿐이고,
`env` 형태 다섯 중 **점 표기 축 1024**(`anomalyDottedEnv`)와 **우변 비-인라인 축 1024**
(`anomalyEnvNotTable`)는 무변경으로 빠져 산출이 입력과 바이트 동일이다. 그 위에서 P0는 같은
바이트를 두 번 훑고, P1·P2·P3는 파일을 자기 자신과 비교하며, P4는 자명하게 성립한다 —
§2.3이 세는 다섯 형태 중 **둘이 되쓰기를 한 번도 지나지 않았다.**
수리는 둘이다. ① 케이스마다 "기입했거나, 아니면 산출이 입력과 바이트 동일"을
`assertCodexOracles`가 건다. ② 그것은 **필요조건일 뿐이므로**(이상 판정이 넓어져 **유효한**
케이스가 기입 집합에서 공회전 집합으로 옮겨가도 ①은 통과하고 폭 5120도 그대로다)
`TestCodexLatticeWritingBranchCount`가 **개수 3072를 못박는다.** 그 이주가 바로 이 브랜치가
이미 낸 실패다(과발화하는 이상 판정). **그 수는 현재 트리에 대한 진술이다** — 과발화를 고치면
케이스가 기입 집합으로 되돌아와 수가 **올라가고**, 그때 값을 올리는 것은 예정된 작업이지
단정을 느슨하게 하는 것이 아니다. 수가 **내려가면** 그것은 회귀다.

**B — P3의 면제가 감시 대상을 덮었다.** 인라인 `env` 논리 엔트리를 통째로 면제하는데, 그
엔트리가 뒤따르는 `[table]` 헤더를 삼킨 상태에서는 그 면제가 **사용자 자신의 라인**까지
덮는다. 실측: 산출이 `[other]`와 그 키를 통째로 잃은 입력에서 손실 목록이 **비었다**(다른 네
겹도 침묵 — 그 입력은 파스되지 않아 P1이 비대칭 계약으로 건너뛰고, 주석이 없어 P2가 볼 것이
없으며, P0는 엔트리 구조만 보고, P4는 이미 상한 산출 위에서도 성립한다). 수리는 위 P3 절의
두 좁힘이다.

> **수리된 겹에는 그 모양을 먹이는 픽스처가 없었다(session-54).** 좁힘 뒤 P3는 이 손실을
> 잡을 수 있게 됐지만, 그 형태를 담은 커밋된 픽스처가 하나도 없어 그물은 그대로 초록이었다 —
> **잡을 수 있다는 것과 잡는다는 것은 다르다.** `TestCodexHeaderInsideInlineEnvOracles`가 그
> 자리를 채운다(픽스 전 P3 적색 · 픽스 뒤 무변경으로 다섯 겹 성립). 짝으로
> `TestCodexHeaderShapeInValueStillWrites`가 오경보 쪽을 지킨다 — 좁힘이 여러 줄 값의 정상적인
> 이어지는 줄까지 얼리면 사유가 참이어도 새 결함이다.

**C — P2가 여러 줄 문자열이 닫히는 물리 라인을 통째로 건너뛰었다.** 줄 머리 상태를 **걸음
전에** 물어서다. 실측: 인라인 `env`가 `} # keep this note`와 같은 줄에서 `"""`를 닫는 파일에서
주석 수집이 **0개**를 내고, 그 주석을 산출에서 지워도 여전히 0개다 — 주석 손실을 잡으라고 있는
겹이 바로 그 손실에 눈이 없었다. 생산 쪽은 같은 모양의 결함을 이 릴리스가 이미 고쳤으므로
(`advance`가 문자열 밖 `#` 자리를 낸다) 기제를 새로 세우지 않고 그대로 쓴다.

**D — P1이 빈 인라인 `env`에 오경보를 냈다.** 허용 경로에 env 테이블의 **부모 경로**가 없고,
평탄화는 빈 테이블을 그 경로의 **잎**으로 적는다(소실을 보려면 잎이어야 한다). 그래서
`env = {   }`는 install이 옳게 동작해도 `경로가 사라졌다`로 적색이었다. 결과는 적색 빌드가
아니라 **커버리지 구멍**이다: TOML의 후행 쉼표 금지 때문에 **전용 생산 로직**을 가진 빈 인라인
갈래를 격자에도 어떤 오라클 픽스처에도 넣을 수 없어 다섯 겹 전부에서 빠져 있었다. 수리는
**입력의 그 경로가 실제로 빈 테이블일 때만** 부모 경로를 허용하는 것이다 — 무조건 허용하면
`env = []` 같은 비-테이블 우변도 같은 경로의 잎이라 그 값의 변조가 P1에 보이지 않게 된다.

**격자 케이스 수는 5120 그대로 두고 겨냥 픽스처만 더했다**(폭 고정 단정을 지키는 선례를
따른다): `TestCommentsOnMultilineStringCloseLine` · `TestLineSurvivalEntryExemptionStopsAtHeader`
(둘 다 **오라클 자신을 재므로** 생산 코드 수정과 무관하게 초록이다) ·
`TestCodexEmptyInlineEnvOracles` · `TestCodexMultilineStringCloseOracles`.

> **교훈은 "겹을 더 쌓아라"가 아니다.** 넷 중 셋(A·B·C)은 겹이 **있는데 그 자리에서 눈을
> 감은** 것이고, 하나(D)는 겹이 **오경보를 내서 형태를 검증 밖으로 밀어낸** 것이다. 겹마다
> "이 겹은 언제 아무것도 재지 않는가"를 묻는 자리 — 오라클 자신을 재는 테스트와 공회전
> 개수 — 가 겹의 수보다 먼저다.

### 2.3 입력 — 새 의존 없이 결정적 조합 격자

축의 곱으로 만든다. 각 축 3~4개면 수천 케이스이고 `-p 1`에서 1초 미만이다.

```
env 형태 : 헤더 / 인라인(1줄) / 인라인(여러 줄) / 점 표기 / 우변 비-인라인
사용자 키: 0 / 1 / 3개        키 표기: bare / "basic" / 'literal' / A.B / 공백 담은 따옴표
값       : '#' 포함 / ',' 포함 / 정수 / 여러 줄 배열 / 중첩 인라인
주석     : 없음 / 후행 / 앞줄 독립 / 둘 다
바이트   : LF / CRLF · 마지막 줄 종결자 유무 · 선두 BOM 유무 · 들여쓰기 유무
```

**property-based 라이브러리를 새로 들이지 않는다**(D8 의존 예산). 격자는 재현성이 공짜이고
실패 케이스가 곧 최소 케이스라 shrink가 필요 없다. 이 격자가 §1.3 선행 게이트 1의 판정 수단을
겸한다.

**폭(5120)과 깊이(기입 갈래 3072)를 둘 다 못박는다.** 폭만 고정하면 케이스가 무변경 이탈로
옮겨가 아무것도 재지 않아도 초록이다 — 첫 축의 다섯 형태 중 둘이 실제로 그 상태였다
(§2.1 "그물 자신의 구멍 넷" A). 새 형태를 재려면 **축이 아니라 겨냥 픽스처를 더한다**:
축을 더하면 케이스 수가 바뀌어 폭 고정 단정이 무의미해진다.
