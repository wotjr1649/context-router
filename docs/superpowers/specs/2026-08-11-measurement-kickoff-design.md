## 0. 왜 이것이 필요했나

v0.20.0은 회수 실적을 재는 눈금을 만들었지만 스스로 재기 시작하지 않는다. CHANGELOG
`[0.20.0] 업그레이드 주의`의 셋(설치본 교체 · `CTR_SHADOW_RETENTION=336h` ·
`legacy_after_migrate` 확인)이 §2다.

개시 직전 실측이 그 구간의 전제를 흔들었다 — **이 프로젝트에서 `ctr_fetch`가 12일간 0회**였고
(§1.1), D104 착수 조건의 `resolved_artifacts + missed ≥ 10`을 14일에 채울 근거가 없다.
**구간이 행 2("창을 sizing하기에 채택이 부족하다")로 끝날 것을 알면서 시작한다** — 소유자 판정
(2026-08-11), 설계서 §D104 착수 조건 ★에 제자리 기록했다. 개시 비용이 거의 0이고, 시작하지
않으면 그사이 아무것도 쌓이지 않기 때문이다.

### 0.1 성공 기준 (소유자 승인, 2026-08-11)

> **이 머신에서 `ctr_fetch`가 "회수하지 않았으면 실제로 비용을 물었을 자리"에서 최소 한 번
> 호출되고, 그 호출이 D103 계측으로 원장에 남는 것.**

★ **그 회수가 기여하는 곳은 채택 문턱(`resolved_artifacts + missed`)이지 나이 분포가 아니다.**
나이 분위수와 `shadow_*` 칸의 모집단은 **shadow 귀속 + 나이 기록된 해소**로 제한되는데(D103
계약 2 ★★), "비용을 물었을 자리"의 회수는 explicit 소스가 붙은 대상일 가능성이 높다. **둘을
헷갈리면 채택 질문에 창 질문의 수로 답하게 된다.**

★ **그런 자리가 한 번도 오지 않으면 그것은 채택 질문의 답이고, 창 판단은 행 2대로 열려 있다** —
결정표에는 질문을 봉인하는 권한이 어디에도 없다.

## 1. 개시 전에 잰 것 — 다시 재지 않는다

전부 2026-08-11, 이 머신.

### 1.1 라이브 원장 `[실측 — go run ./cmd/context-router stats]`

```
ctr_search              59회   ~2026-08-08T21:37:43Z
ctr_fetch               49회   ~2026-07-30T14:34:20Z      ← 12일간 0회
ctr_session_summary      5회   ~2026-07-23T12:22:28Z
fetch  calls=49  나머지 전부 `미이관`                      ← 결정표 행 0
```

**열 셋이 아직 없었다** — 설치본이 0.19.1이고 `stats`는 원장을 read-only로만 연다. 설계서
§D104 착수 조건 ★★가 2026-08-10에 예언한 모양 그대로이고, **행 0의 예외**(열은 다 있는데
워터마크만 없어 F2 축이 영구 판정 불가가 되는 상태)에는 걸리지 않은 깨끗한 시작점이었다.

★★ **"회수가 12일간 0회"는 이 프로젝트 원장에 한정된 참이다.** 같은 머신의
`D:\AI_DEV\codex-conductor-cc` 원장에는 **`ctr_fetch` 11회**가 있다 `[실측 — 그 디렉터리를
cwd로 stats 실행]` — 2026-08-08T13:20:32Z~13:23:38Z, **7분 사이의 한 세션 버스트**이고 같은
세션에 `ctr_export_events` 104회가 함께 돌았다. 초안은 원장 **파일 크기**로 "다른 원장에 셀 것이
없다"고 판단했는데 그 추론은 무효이고(2페이지 원장에도 수십 행이 들어간다), 실제로 반례가
나왔다. 스토어는 23개가 아니라 **24개**다(16,384 B 하나 · 8,192 B 11개 · 4,096 B 12개).

### 1.2 사슬 진단 — 세 고리 중 하나만 끊겼다

| 고리 | 상태 | 증거 |
|---|---|---|
| 1. 포착 | **작동** | 이 세션의 `go test` 출력이 `shadow:Bash:…` 소스로 포착됨 `[실측 — ctr_search]` |
| 2. 검색 | **작동** | `ctr_search`는 상시 로드이고 질의 하나에 3건 반환 `[실측]` |
| 3. 회수 | **안 돎** | 위 12일 0회. 이 세션의 컨트롤러도 부르지 않았다 — 스니펫으로 충분했다 `[관찰]` |

★ **정확한 진단은 "이 제품이 이 머신의 작업과 안 맞는다"가 아니다.** §1.1 ★★가 보인 패턴
(`ctr_export_events` 104회 → `ctr_fetch` 11회 = 세션 이벤트를 대량으로 훑고 일부를 회수)은
**회수가 값을 내는 작업이 실재한다**는 증거다. 맞는 진술은 **"자기 프로젝트를 개발하는 세션에서는
쓸 일이 적고, 다른 종류의 작업에서는 쓴다"**이다. 다만 그쪽도 8/8 이후 회수가 없어 **어느 원장도
지속적 회수 트래픽을 갖지 않는다** — D104 ★F11이 그 경우를 이미 규정한다.

### 1.3 반증한 가설 둘 — 다시 세우지 않게 기록한다

**① "지연 로드(D99)가 회수 0의 원인이다" — 반증** `[실측 — 태그 날짜 대조]`. `v0.19.0`
태그는 2026-08-08 14:33 KST, 배포본 교체는 8/8 16:08, `ctr_fetch` 마지막 호출은 7/30 23:34
KST다. **7/30~8/8의 약 9일은 전 도구가 상시 로드였고 그 구간에도 0회다.**

**② "큰 출력이 1 MiB 상한에 걸려 포착되지 않는다" — 반증** `[실측 — 프로젝트 drops 집계]`.
drops 400줄 중 `shadow-oversize`는 **0건**(399건이 `unknown-session` — shadow drop이 아니라
지금은 소멸한 세션 식별 실패, 1건이 `shadow-ingest`). 7/30 11:26 이후 그 로그는 비어 있다.
★ 다만 이것은 **프로젝트 로그 한정**이다 — 스토어 루트에 별도 drops 로그가 있고 8/8 16:08까지
31줄(`bad-input`·`bad-session-id`)이 있다.

### 1.4 대신 드러난 기제 — 필터링이 포착을 막는다 `[관찰]`

컨트롤러가 `gh run view --log-failed`를 **두 번** 호출했다(같은 로그, 다른 필터). 크고 재현에
수십 초가 드는 로그 — **회수가 값을 냈을 자리다.** 그런데 파이프라인 최종 stdout이 4줄이었고,
훅이 보는 것은 그것이므로 **하한 미달로 조용히 스킵**된다(`shadowCapture`가 `size <= 하한`에서
drop 없이 반환 — **정확히 하한값도 스킵**). 하한·상한은 16 KiB·1 MiB이되 고정값이 아니다:
`shadowLimit`이 `CTR_SHADOW_MIN`·`CTR_SHADOW_MAX`로 덮는다(양의 정수만).

**컨텍스트를 아끼려는 필터링이 포착 기회를 지운다** — 이 제품의 가치 제안과 모델의 자연 행동이
같은 문제를 서로 다른 방법으로 푼다. 이 기제는 D100이 열거한 채택 레버 어디에도 없다.
**다음 릴리스 범위의 입력이다**(§6).

### 1.5 전제 하나가 거짓이었다 — 기록자가 여럿이다 `[실측 — 프로세스 목록]`

초안은 "이 세션이 유일한 기록자"를 전제했다. 2026-08-11 15:08에 실행 중인 `context-router.exe`가
**8개**였고 부모는 `claude.exe` 1 · **`codex.exe` 7**이었다. 그 수는 **단조 증가**했다 — 교차모델
검토를 돌린 것이 15:2x에 14개로 늘렸고, 작업이 끝난 뒤에도 서버는 정리되지 않았다. 프로젝트 ID는
`ident.Canonicalize`가 git worktree를 주 저장소로 접으므로 워크트리 세션도 **같은 원장**이다.

**뜻하는 바**: 호스트 하나만 재시작하면 나머지 호스트의 옛 서버가 살아남아
`legacy_after_migrate`를 계속 올리고, 행 0b의 판정 기준("증가하는가")이 영영 닫히지 않는다.
**§2가 이 전제 위에서 다시 쓰였고, 그것이 실행 결과를 갈랐다.**

## 2. 실행한 것 — 순서와 결과 (2026-08-12)

| # | 무엇 | 결과 |
|---|---|---|
| 1 | `CTR_SHADOW_RETENTION`을 **User 스코프**에 `336h` | ✅ 레지스트리 읽기로 `-ceq '336h'` 확인. **`14d`는 안 된다** — `time.ParseDuration`의 유효 단위는 `ns`·`us`·`ms`·`s`·`m`·`h`뿐이고 `d`가 없으며 `[문서 — pkg.go.dev/time#ParseDuration]`, `store.ShadowRetention`은 파싱 실패를 **조용히 삼키고 72h로 떨어진다** |
| 2 | **모든 `context-router` 프로세스를 0으로** | ✅ 소유자가 Codex 호스트(PID 1개, 서버 7개)를 트리째 종료. 그 과정에서 이 세션의 MCP 서버도 정리되어 **0개**가 됐고, 그 결과 ctr 도구가 끊겨 "설치와 재시작 사이에 ctr 도구를 부르지 않는다"가 **기계적으로 보장**됐다 |
| 3 | `context-router.exe.old`(0.19.0) 제거 → 현행(0.19.1)을 `.old`로 → `go install` | ✅ `version` = **0.20.0** |
| 4 | 서버를 **한 번** 기동시켜 이관을 일으킴 | ✅ `$env:CTR_SHADOW_RETENTION='336h'`를 준 채 빈 stdin으로 띄워 즉시 EOF 종료. `[ctr] v0.20.0 … root=<이 저장소>` 확인 |
| 5 | `stats`로 이관 결과 확인 | ✅ §3 |

### ★ 4번이 필요했던 이유 — `stats`는 이관을 돌리지 않는다

3번 직후 `stats`는 여전히 전부 `미이관`이었다. 이관을 도는 것은 `store.OpenContext(writable)`인데
`stats`는 read-only로만 열고, 훅은 **하한을 넘는 출력이 있을 때만** writable로 연다. 초안은 이
자리를 "5번 뒤 첫 훅이 이미 이관했을 것"으로 적었는데 **그 가정이 틀렸다.**

**그리고 4번에 환경 변수를 명시적으로 준 것이 핵심이다.** 그 셸은 호스트가 뜬 시각(10:13)의 환경
블록을 상속했고 User 스코프 값은 그 뒤에 걸렸다 — 그대로 띄웠으면 **기동 퍼지가 72h로 돌아
336h가 지키려던 나이 분포의 머리를 되돌릴 수 없이 지웠을 것이다.** MCP 서버는 매니페스트에 `env`
블록이 없어 호스트의 환경 블록을 그대로 상속한다.

### ★★ 되돌릴 수 없는 상태 둘을 피했다

2번(프로세스 0)이 없었으면 옛 서버가 워터마크 뒤에 `ctr_fetch` 행을 남겨 **행 0b가 영구 발화**할
수 있었고, 워터마크 쓰기가 락 경쟁에서 지면 **행 0의 예외(F2 축 영구 판정 불가)**에 빠질 수
있었다. §3이 둘 다 통과했다.

## 3. t0 기준선 (확정)

**t0 = `2026-08-12T01:22:18Z`** (= 2026-08-12 10:22:18 KST, 원장 mtime = 이관 시각)

```
fetch  calls=49  legacy=49  legacy_after_migrate=0  resolved=0  resolved_artifacts=0
       missed=0  shadow_rows=0  shadow_artifacts=0  age_s p50=없음 p90=없음 max=없음
total  198회
```

**판정**: 여덟 칸 전부 숫자(행 0 탈출) · `legacy_after_migrate`가 **표식을 가짐**(행 0의 예외
회피) · 그 값이 **0**(행 0b 회피) · 실효 보존값 336h.

**`age_s`의 `없음`은 정상이다** — D103 계약 9: *"수를 세는 칸이 다 숫자인데 `age_s`만 `없음`이면
그것은 **측정값**이다(귀속 해소 표본이 0건) — 완전 이관 직후, 즉 측정 구간 첫날의 정상 상태"*.
`legacy=49`도 이관 전 49행이 전부 레거시로 분류된 예상 결과다.

★ **뺄셈은 쓰지 않는다.** `LedgerFetchStats`의 어느 질의에도 `ts` 술어가 없어 회수 줄은 원장
수명 전체의 누적인데, **D104가 읽는 칸의 t0 값이 전부 0이므로 t0 이후의 모든 회수가 곧 구간
데이터다.** 0이 아닌 것은 `calls`·`legacy`뿐이고 그 둘은 착수 조건이 읽지 않는다.
(초안은 `증분 = 종료값 − t0값`을 적었으나 네 갈래 검토가 전부 반증했다 — distinct 계수는 구간에
걸친 아티팩트 때문에 하한이 되고, 분위수는 뺄셈이 아예 무의미하다. 여기서는 t0 값이 0이라
그 문제가 발생하지 않는다.)

★ **`legacy_after_migrate`의 t0 값 `0`이 행 0b 증가 판정의 기준선이다.** 그 수는 누적이고 0으로
돌아가지 않으므로, 판정은 값이 아니라 **이 기준선보다 늘었는가**로 한다.

## 4. 다음 세션이 할 것

### 4.1 재시작 직후 — 서버가 실제로 떴는지, 환경을 받았는지

호스트를 재시작한 뒤 **가장 먼저**:

1. `Get-Process context-router`로 서버가 떴는지. 재시작이 훅의 스토어 잠금과 겹치면
   `lockStoreCtx`의 **5초 하드 한도**를 넘겨 기동에 실패할 수 있고, 조용히 넘어가면 14일 동안
   회수가 아예 불가능해진다.
2. **재시작한 호스트 안에서** `$env:CTR_SHADOW_RETENTION`을 읽어 `336h`인지. 서버는 호스트의 환경
   블록을 상속하므로 이것이 서버 실효값의 **직접 증거**다(별도로 띄운 CLI의 `doctor [14]`는 그
   프로세스 자신의 환경이라 다른 이야기다).
3. `go run ./cmd/context-router stats`로 `legacy_after_migrate`가 여전히 **0**인지 — 늘었으면
   어딘가에 옛 서버가 남아 있다는 뜻이고, 처방은 그것을 찾아 끄는 것이다.

### 4.2 회수 검증 — **판정 대상이 아닌 프로젝트에서**

계측은 프로덕션에서 회수를 한 번도 기록한 적이 없다(테스트로만 검증됐다). 그런데 검증용 회수를
판정 대상 원장에서 하면 **그 행이 착수 문턱과 나이 분포에 영구히 남는다** — 원장에는 "검증용"을
표시할 열이 없고 행을 지우는 경로도 없다.

**회수 계측은 프로젝트 단위로 완전히 갈린다** `[실측 — LedgerFetchStats가 받는 것은 프로젝트
디렉터리 하나이고, 그 ID를 정하는 것은 서버 인자가 아니라 호스트 세션의 cwd다]`. 따라서 **다른
프로젝트를 cwd로 하는 세션에서 회수하면 판정 대상 원장은 한 행도 받지 않는다.** 코드 경로는 같은
바이너리·같은 함수·같은 분기다.

## 7. 검토 이력과 미해결

### 7.1 무엇이 있었나

초안(`f4a32d1`)이 내부 검토 셋 + 교차모델 패스를 받아 1차 수정, 그 판이 다시 내부 셋 + 교차모델

**1차** — 네 갈래가 독립적으로 같은 결함에 닿았다: 검증용 회수가 착수 조건과 나이 분포를 오염

정정됐다.
