## 0. 결정 이력 (v0.12 신규 — D62까지는 v0.11 설계서·이전 델타 체인)

- **D63** 라우팅 채택 — 도구 가시성과 계측:
  - **문제 정의**: 채택 부진의 원인을 "언제 쓸지 모른다"로 단정하지 않는다.
    훅 경로가 정상 동작하는 상태에서 명시적 호출만 희소하므로, 1차 가설은
    **도구가 지연 로드(tool search)라 컨텍스트에 보이지 않는다**이다. 가설은
    가설로 취급하고 아래 순서로 검증한다.
  - **① 계측 교정을 선행한다**(검수 F10). 현행 `runUsageAdoption`은 `ctr_`
    **부분 문자열**로 버킷팅해 `mcp__ctr__*`와 `mcp__ctr-exec__*`를 한 카운터에
    합치고, 세션별 노출 상태도 자격 세션 분모도 남기지 않는다. 이 상태로는
    가설을 **확인도 반증도 할 수 없다**. → **서버 네임스페이스 접두 단위
    버킷팅** + **세션별 노출 상태 기록**. 교정 후에는 서버 등록 형태의 차이가
    그대로 사용자 내 비교가 된다.
  - **② 서버 등록 단일화**(검수 F4·F5). `.mcp.json`이 `ctr`(6도구·10,466B)와
    `ctr-exec`(8도구·12,914B)를 **동시에 등록**해 6도구가 중복 노출된다.
    `ctr_execute`/`ctr_execute_file`은 후자에만 존재하므로 전자에 상시 로드를
    걸어도 exec 채택은 변하지 않는다. → **단일 서버 등록**을 표준 형태로 하고
    설치기(D64)가 이 형태를 생성한다. (2026-07-25 로컬 선반영.) 서버 이름은
    설치기가 고정하는 값으로 정한다 — 이름이 바뀌면 permission 규칙 접두와
    doctor 안내 문면이 함께 움직이므로 D64에서 한 번에 확정한다(현재 로컬은
    `ctr-exec` 유지, 코드 변경 없음).
  - **③ 상시 로드 적용 + 전후 비교**. 단일 서버에 `alwaysLoad: true`. 상주
    비용은 **등록된 서버들의 합집합**으로 측정한다 — 게이트 11의 12,914B는
    **단일 서버 tools/list 표면**이며 클라이언트 상주 총량과 다르다(F5).
    롤백 임계를 그 총량 기준으로 명시한다.
    - **호스트 요건 2건**(2026-07-25, 호스트 문서 확인): `alwaysLoad`는 **Claude
      Code v2.1.121 이상**을 요구하고 그 이하 호스트는 이 키를 조용히 무시한다.
      또 이 키는 **서버가 연결될 때까지 세션 시작을 막는다 — 호스트 표준 5초
      연결 타임아웃이 상한**이다. 후자가 D67 기동 회수를 `mcp.Serve` 밖 고루틴으로
      옮기고 `startupPurgeBudget`을 "세션 시작 지연 한도"가 아니라 폭주 가드로
      재정의한 근거다(둘 다 이 브랜치의 결정).
  - **④ SessionStart 안내는 조건부**. ①③으로 가시성이 채택을 설명하면 안내
    문구는 도입하지 않는다(YAGNI). 도입할 경우 제약:
    - **호스트 게이트 필수**(F6) — Claude·Codex 훅이 하나의 Run/dispatch와
      하나의 stdout writer를 공유하므로, Claude 형식 출력은 host가 Claude일
      때만 쓰고 그 외에는 stdout을 비운다. 호스트별 골든 테스트로 고정한다.
    - **상한은 호스트 문서값 아래로 앵커**(F8) — `additionalContext`는 10,000자
      초과 시 파일로 스필되고 프리뷰만 노출된다. 독립적인 숫자를 고르지 않는다.
    - **누락이 관측 가능해야 한다**(F7) — EnsureSession 실패·데드라인 경로는
      drop 한 줄과 exit 0으로 끝나므로, 그 경로에 안내를 얹으면 조용히 사라진다.
  - **범위 제한**: 안내 대상은 **ctr 고유 기능**으로 한정한다(프로젝트 영속
    저장·byte-exact fetch·격리 exec·세션 이벤트). 다른 도구와 겹치는 표면을
    다시 라우팅해 중복 호출을 만들지 않는다.

- **D64** 설치·업데이트 원커맨드 + exec 승인 정책:
  - **문제**: MCP 등록·승인·exec 활성화가 수동 편집으로 남아 있다. 훅 블록에는
    `__ctrManaged` 마커가 붙지만 **`permissions.ask`에는 마커가 없다**(실측) —
    설치기 관리 밖이라 갱신도 진단도 되지 않는다.
  - **원커맨드**: 기존 hook install의 **멱등 병합 · 관리 블록 · 버전 마커**
    인프라를 `.mcp.json`과 호스트 승인 키까지 확장한다. 설치와 업데이트는 같은
    명령이며(멱등), 마커 불일치는 self-heal 한다(doctor `[16]`·`[17]`이 이미
    불일치를 표시한다).
  - **스코프 규칙**(검수 F9 — plan_conflict, 사람 판단으로 확정): 배열 설정이
    스코프 간 병합된다는 일반화는 **틀렸다**. 병합되는 것은 permission
    `allow`/`ask`/`deny`뿐이고, `enabledMcpjsonServers` 같은 일반 배열 설정은
    **가장 높은 우선순위 스코프가 통째로 override** 한다. → 설치기는 사용 중인
    최고 우선순위 스코프에 쓰거나, 더 좁은 스코프의 기존 정의를 **감지해
    보고**한다. 무시될 값을 조용히 기록하지 않는다.
  - **MCP 등록 스코프 모델**(2026-07-25 호스트 문서 `code.claude.com/docs/en/mcp.md`
    확인 — 이 설계서는 `.mcp.json`=프로젝트 스코프만 전제한 채 모델을 적지 않았다):

    | 스코프 | 저장 위치 | 승인 필요 |
    | --- | --- | --- |
    | local(기본) | `~/.claude.json`의 `projects.<경로>.mcpServers` | 아니오 |
    | **project** | **`.mcp.json`**(저장소로 공유) | **예 — `enabledMcpjsonServers`가 게이트하는 대상** |
    | user(예전 "global") | `~/.claude.json` 최상위 | 아니오 |

    우선순위는 local > project > user이며, 가장 높은 우선순위 스코프의 **항목이
    통째로 이긴다 — 필드는 스코프 간 병합되지 않는다**(병합되는 예외는 위 스코프
    규칙의 permission 규칙뿐이다).
    - **전역 사용은 user 스코프 + 공식 CLI로 해결한다**(사람 판단, 2026-07-25):
      `claude mcp add --scope user ctr-exec -- context-router --enable exec`.
      `~/.claude.json`은 Claude Code의 주 상태 저장소이므로 **거기 쓰는 일은 설치기
      범위 밖**이다. user 스코프 서버는 사용자가 직접 넣은 것이라 승인 절차가 없다 —
      `enabledMcpjsonServers`는 저장소가 제공한 프로젝트 스코프 서버를 승인하는 키다.
    - **워크스페이스 신뢰**(검수 발견): 호스트 **v2.1.196 이후**, 저장소에 커밋된
      `.claude/settings.json`의 `.mcp.json` 승인은 **워크스페이스를 신뢰한 뒤에만**
      유효하고 `~/.claude/settings.json`의 승인은 신뢰하지 않은 폴더에서도 적용된다.
      이는 결함이 아니라 **의도대로 동작하는 보안 모델**이다 — 신뢰받지 않은 저장소가
      스스로를 승인하지 못하게 한다. 설치기가 user 스코프 쓰기를 하지 않기로 한 판단과
      같은 방향이다.
  - **승인 정책**(사용자 지시, 2026-07-25): **설치기는 `permissions.ask`를
    생성하지 않는다.** exec 승인 강도는 호스트 권한 모드가 정한다.
    - 근거: `bypassPermissions`는 프롬프트와 안전 점검을 끄지만 **명시적 ask
      규칙은 이 모드에서도 프롬프트를 강제**한다. 규칙 평가는 deny → ask →
      allow 순이고 첫 매치가 결과를 정하므로 **더 구체적인 allow도 ask를 이기지
      못한다**. 실측에서 `ask` 2종과 `allow` 1종이 공존해 allow가 무력화된
      상태였다.
    - **이중 동의는 유지**한다: ① `--enable exec` 서버 프로필(기동 시) ② 호스트
      권한 모델(모드와 permission 규칙에 따름). D58의 "삼중 게이트" 중 호스트 ask
      층은 **모드·규칙 존중**으로 대체된다 — default 모드에서는 MCP 기본 프롬프트가
      그대로 작동하지만, 즉시 실행이 무프롬프트 모드 전용은 **아니다**: exec 도구를
      덮는 `allow` 규칙(프롬프트의 '다시 묻지 않기'·`--allowedTools`가 남기는 항목)이
      있으면 default 모드에서도 프롬프트 없이 실행된다. 그래서 ②는 두 경우에 동의
      순간을 만들지 않는다 — 무프롬프트 모드, 그리고 덮는 allow가 있는 default 모드.
      설치기가 ask 안내를 걷어내는 일이 실효를 갖는 까닭도 여기 있다: 실측 환경은
      `ask` 2종이 `allow` 1종을 가리고 있었고, ask를 지우면 잠들어 있던 그 allow가
      유효해진다.
    - exec 도구에 `_meta["anthropic/requiresUserInteraction"]`을 **붙이지
      않는다** — 붙이면 bypass에서도 프롬프트가 강제되어 위 정책과 모순된다.
    - doctor 호스트 스니펫을 ask 기반 문면에서 **모드 기반 안내**로 개정한다
      (D58에서 넣은 `permissions.ask` 예시가 대체 대상).
    - **설치기는 강제 프롬프트 경로를 제공하지 않는다**(2026-07-25 계획 검수에서
      개정 — 초안의 `--exec-approval=ask` opt-in 철회). 실사용 방향이 "무프롬프트
      모드에서 즉시 실행"이고 그 반대 방향 opt-in에는 수요가 없다. 강제 프롬프트를
      원하면 사용자가 settings의 `permissions.ask`에 직접 적는다 — 그 결과가
      무프롬프트 모드에서도 프롬프트를 만든다는 것은 위에 적힌 그대로다.
    - **doctor 신설 진단**: ask 규칙이 allow를 가리는 조합을 감지해 보고한다.
      사용자가 스스로 알아채기 어려운 형태이며 실제로 발생했다.
  - **exec 활성화**는 명시 opt-in 플래그를 유지한다(기본 OFF, D58 계승).
  - **대상 환경**: 소유자 본인 머신들. 낯선 사용자를 위한 배포 채널은 비범위
    (§1.2).

- **D65** 툴체인 사용자 구성 격리 일반화:
  - **구조적 갭**: D59의 env allowlist는 닫힌 표로 잘 동작하지만, 그 표가
    통과시키는 `APPDATA`·`USERPROFILE`·`LOCALAPPDATA`(Windows)와 `HOME`(Unix)이
    **호스트 구성 파일로 가는 포인터**다. 즉 환경변수는 닫혔고 **파일 기반
    툴체인 구성은 열려 있다**. v0.11.1은 csharp 한 사례만 국소 차단했다.
  - **일반 규칙**: 러너별로 사용자 구성 파일 경로를 스크래치에 고정한다.
    - **go**: `GOENV`를 스크래치로 재지정(F11). 현재 `GOCACHE`·`GOPATH`·
      `GOTMPDIR`만 재지정하므로 호스트 go env 파일이 `GOFLAGS`·`GOPROXY`·
      `GOTOOLCHAIN`을 그대로 공급한다 — 빌드 동작과 재현성에 직접 영향한다.
    - **node/bun**: 사용자 npmrc 경로를 스크래치로 재지정.
    - **python**: user-site 비활성 + 구성 파일 경로 고정.
    - **pwsh**: `PSModulePath`를 호스트와 무관한 값으로 명시 고정한다(F12). 갭은
      호스트 값이 그대로 복사되어 호스트 설치 모듈이 자동 로드되는 것이었고, 닫힌
      표에서 키를 빼는 것만으로는 부족하다 — 값이 없으면 인터프리터가 호스트
      상태에서 유효 경로를 스스로 재구성한다.
      - **주입 값은 세 항목, 이 순서다**: ① 스크래치 하위의 **빈** 모듈
        디렉터리(사용자 모듈 슬롯) ② 인터프리터 설치본 `<PSHOME>\Modules`
        ③ 머신 전역 `<ProgramFiles>\<PowerShell|WindowsPowerShell>\Modules`
        (버전별 갈래). ③은 사용자 구성이 아니므로 D65가 닫는 대상이 아니며,
        `ProgramFiles`가 비면 ③을 빼고 준다.
      - **①이 필요한 이유는 측정된 정지다**(2026-07-25, GitHub `windows-latest` +
        Windows PowerShell 5.1 실측): 사용자 모듈 슬롯이 비어 있으면 프로바이더
        cmdlet(`Set-Content`)이 **예외도 오류 레코드도 없이 돌아오지 않는다** —
        파이프라인과 `[IO.File]::WriteAllText`는 정상 반환하고 인터프리터 기동도
        정상이다. 상속 값 8항목의 항목 단위 이분탐색 결과 정지를 푸는 항목은 단
        하나, 호스트 **사용자** 모듈 경로였다. 그 값의 주입은 D65가 금지하므로
        "슬롯이 채워져 있어야 한다"는 요건만 우리가 만든 빈 디렉터리로
        만족시킨다 — 호스트 경로가 아니어서 자동 로드될 모듈이 없다.
      - **①을 지워 한 항목으로 "단순화"하지 말 것**: 그 순간 3-OS CI의 Windows
        잡이 오류 출력 하나 없이 무한 정지로 되돌아간다. 값을 넓히는 것도 교정이
        아니다 — 인터프리터가 머신 전역 항목을 스스로 앞에 덧붙이므로 자식의 유효
        값은 이미 주입 값보다 넓다. 재발 판별 계측은
        `internal/sandbox/run_windows_test.go`의 probe-env 두 변종이다.
      - **`USERPROFILE`도 스크래치로 돌린다**(shell 러너 한정): `PSModulePath`를

        경로를 앞에 덧붙이므로(실측), 호스트 사용자 모듈을 실제로 떼어내는 레버는

    - **csharp**: v0.11.1의 스크래치 `nuget.config` 유지.
  - **적용 실증 테스트**(v0.11.1 교차 검수가 노출한 갭): 구성 파일의 *생성*이

- **D66** shell 방언·종료코드 계약:
  - **방언**: `language: "shell"`은 플랫폼 기본 셸이다 — Windows는 PowerShell
    (pwsh 7, 부재 시 Windows PowerShell 5.1 폴백), 그 외는 sh. v0.11.1에서
    스키마 문면에 표기했다. 정확한 인터프리터·버전은 응답 `runner` 필드가 준다.
  - **종료코드 계약 — (a) 현행 유지로 확정**(2026-07-25). shell 계열의
    `exit_code`는 **스니펫의 종료 상태**이며 중간 비종결 오류를 대표하지
    않는다. 성공 판정은 `exit_code`와 `stderr`를 함께 보고 한다.
    - 이는 러너 결함이 아니라 **셸 일반의 정의된 동작**이다 — POSIX sh도
      `false; echo hi`가 0을 반환한다. PowerShell 고유 문제로 다루면 러너가
      언어별로 다르게 굴어 오히려 예측이 어려워진다.
    - **안전망 공백 — Windows 인터프리터의 예외**(리뷰어 2명과 구현자가 독립
      실측. 사람 판단: **문서를 고치고 러너 동작은 바꾸지 않는다**): `exit_code`가
      "마지막 명령의 상태"인 것이 **문자 그대로 성립하는 것은 sh뿐**이다. 러너는
      `pwsh`/`powershell`을 `-File`로 부르는데, 이 호출형은 스크립트가 `exit N`을
      부르거나 종결 오류를 만나지 않으면 0을 돌려준다 — 마지막 줄이 비 0으로 죽은
      **네이티브** 명령이면(`cmd /c exit 5`로 끝나는 스니펫) `exit_code` 0에
      **stderr 0바이트**이고 `$LASTEXITCODE`만 5다. 즉 위 안전망(`exit_code`와
      `stderr`를 함께 보기)이 **이 부류는 잡지 못한다** — 실패가 두 채널 어디에도
      남지 않는다.
      - `$ErrorActionPreference = 'Stop'`도 이 부류를 덮지 못한다 — 스크립트는
        실패한 네이티브 명령을 지나 계속 진행하고 그대로 0으로 끝난다.
      - `$PSNativeCommandUseErrorActionPreference`는 여기서 처방이 아니다: pwsh
        7.6.0 기본값이 False이고 러너는 `-NoProfile`로 시작해 프로필로 켤 수단이
        없다. 버전 사고가 아니라 `-File` 호출형의 고정 성질이다.
      - **실제 처방은 `$LASTEXITCODE` 확인·전파**(예: 마지막 줄 `exit
        $LASTEXITCODE`) — pwsh 7.6.0과 powershell 5.1 폴백 양쪽에서 실측했다.
        계약의 **sh 절반은 정확하다**: POSIX sh는 마지막 명령의 비 0 상태를 문자
        그대로 전파하고, `set -e`는 네이티브 비 0 종료에서도 멈춘다.
      - 러너는 여전히 **아무것도 주입하지 않는다**((b) 유지). 고친 것은 계약 문면과
        doctor 안내이며, 그 안내가 위 처방을 담는다.
    - **(b) 강제 기각**: `set -e` / `$ErrorActionPreference = 'Stop'` 주입은
      파이프라인·조건식·`|| true` 같은 정상 패턴을 깨뜨리는 함정이 많고,
      스니펫 선두 주입은 **오류 메시지의 행 번호를 어긋나게** 한다. 기본값이
      호출자의 정상 스니펫을 깨는 방향은 택하지 않는다.
    - **(c) 신호 필드 기각**: `stderr`가 응답에 온전히 오므로 판정 근거는 이미
      호출자에게 있다. 파생 필드는 매 호출 응답만 키운다.
    - 엄격 동작이 필요하면 **호출자가 스니펫에 직접 적는다**: sh는 첫 줄 `set -e`로
      네이티브 비 0 종료까지 덮이지만, PowerShell은 첫 줄
      `$ErrorActionPreference = 'Stop'`(cmdlet 오류)에 **네이티브 명령용
      `$LASTEXITCODE` 확인·전파**를 더해야 위 공백까지 덮인다. 러너는 강제하지 않는다.
    - 계약 문면은 설계 문서와 doctor 안내에 둔다. 도구 스키마는 게이트 11 여유가
      86B뿐이라(§3) 문면 추가 대상이 아니며, 게이트 재기준화 시 후보로 남긴다.

- **D67** 저장 성장 운영 정책:
  - **신규 메커니즘이 아니다**(검수 F13). 회수 경로는 `purge --older-than
    --vacuum`(D50)으로 이미 존재하고 `--hook-only`는 항상 vacuum 한다. 임계

  - **보존 정책 — 확정**:

    - **자동 경로에서 VACUUM은 하지 않는다.** 삭제로 생긴 free page는 이후

스키마 표면: `ctr` 6도구 10,466B / `ctr-exec` 8도구 12,914B(게이트 11 상한
13,000B). 두 서버 동시 등록 시 상주 총량은 합집합이다.

**관측 기준선 리셋(session-35, D67 구현 중 — 위 session-34 수치의 후속)**: 기동 회수를
측정·검증하는 과정에서 이 저장소의 shadow 적체가 사실상 드레인됐다. 측정·검증 실행을
가로질러 `[15]` shadow 귀속이 844 해시 / 37,545,665B → **18 해시**, 아티팩트 총량이
**1,254 → 20**이 됐고 `[14]` blob 바이트도 그에 비례해 줄었다. 반면 `[14]` `file`은
**210,399,232B로 내내 그대로**다(session-34 말 176,340,992B에서 그사이 성장한 값 —
하루 33–37MB 관측과 일치한다) — 자동 경로에서 VACUUM을 하지 않는 설계가 의도대로
동작한 결과이고(삭제로 생긴 free page는 이후 기록이 재사용한다), blob 축과 파일 축을
따로 두는 이유를 그대로 보여준다. 결과로 **실 store에서 `capped=true`(1회 배치 상한
도달)는 더 재현되지 않으며, D67 임계값 관측은 이 시점부터 새로 쌓는다** — D67은 임계값
결정을 "보존 정책 적용 후 정상상태 관측"으로 미뤄 뒀고, 그 시계가 여기서 리셋됐다.
위 session-34 수치는 지우지 않는다: 리셋 전 그림이 있어야 이 변화가 읽힌다.
