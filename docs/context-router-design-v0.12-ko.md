## 0. 결정 이력 (v0.12 신규 — D62까지는 v0.11 설계서·이전 델타 체인)

- **D63** 라우팅 채택 — 도구 가시성과 계측:
  - **문제 정의**: 채택 부진의 원인을 "언제 쓸지 모른다"로 단정하지 않는다.
    훅 경로가 정상 동작하는 상태에서 명시적 호출만 희소하므로, 1차 가설은
    **도구가 지연 로드(tool search)라 컨텍스트에 보이지 않는다**이다. 가설은
    가설로 취급하고 아래 순서로 검증한다.
  - **① 계측 교정을 선행한다**(검수 F10). 현행 `runUsageAdoption`은 `ctr_`
    **부분 문자열**로 버킷팅해 `mcp__ctr__*`와 `mcp__ctr-exec__*`를 한 카운터에
    합치고, 세션별 노출 상태도 자격 세션 분모도 남기지 않는다. 이 상태로는
    가설을 **확인도 반증도 할 수 없다**. → **서버 네임스페이스 접두 단위
    버킷팅** + **세션별 노출 상태 기록**. 교정 후에는 서버 등록 형태의 차이가
    그대로 사용자 내 비교가 된다.
  - **② 서버 등록 단일화**(검수 F4·F5). `.mcp.json`이 `ctr`(6도구·10,466B)와
    `ctr-exec`(8도구·12,914B)를 **동시에 등록**해 6도구가 중복 노출된다.
    `ctr_execute`/`ctr_execute_file`은 후자에만 존재하므로 전자에 상시 로드를
    걸어도 exec 채택은 변하지 않는다. → **단일 서버 등록**을 표준 형태로 하고
    설치기(D64)가 이 형태를 생성한다. (2026-07-25 로컬 선반영.) 서버 이름은
    설치기가 고정하는 값으로 정한다 — 이름이 바뀌면 permission 규칙 접두와
    doctor 안내 문면이 함께 움직이므로 D64에서 한 번에 확정한다(현재 로컬은
    `ctr-exec` 유지, 코드 변경 없음).
  - **③ 상시 로드 적용 + 전후 비교**. 단일 서버에 `alwaysLoad: true`. 상주
    비용은 **등록된 서버들의 합집합**으로 측정한다 — 게이트 11의 12,914B는
    **단일 서버 tools/list 표면**이며 클라이언트 상주 총량과 다르다(F5).
    롤백 임계를 그 총량 기준으로 명시한다.
  - **④ SessionStart 안내는 조건부**. ①③으로 가시성이 채택을 설명하면 안내
    문구는 도입하지 않는다(YAGNI). 도입할 경우 제약:
    - **호스트 게이트 필수**(F6) — Claude·Codex 훅이 하나의 Run/dispatch와
      하나의 stdout writer를 공유하므로, Claude 형식 출력은 host가 Claude일
      때만 쓰고 그 외에는 stdout을 비운다. 호스트별 골든 테스트로 고정한다.
    - **상한은 호스트 문서값 아래로 앵커**(F8) — `additionalContext`는 10,000자
      초과 시 파일로 스필되고 프리뷰만 노출된다. 독립적인 숫자를 고르지 않는다.
    - **누락이 관측 가능해야 한다**(F7) — EnsureSession 실패·데드라인 경로는
      drop 한 줄과 exit 0으로 끝나므로, 그 경로에 안내를 얹으면 조용히 사라진다.
  - **범위 제한**: 안내 대상은 **ctr 고유 기능**으로 한정한다(프로젝트 영속
    저장·byte-exact fetch·격리 exec·세션 이벤트). 다른 도구와 겹치는 표면을
    다시 라우팅해 중복 호출을 만들지 않는다.

- **D64** 설치·업데이트 원커맨드 + exec 승인 정책:
  - **문제**: MCP 등록·승인·exec 활성화가 수동 편집으로 남아 있다. 훅 블록에는
    `__ctrManaged` 마커가 붙지만 **`permissions.ask`에는 마커가 없다**(실측) —
    설치기 관리 밖이라 갱신도 진단도 되지 않는다.
  - **원커맨드**: 기존 hook install의 **멱등 병합 · 관리 블록 · 버전 마커**
    인프라를 `.mcp.json`과 호스트 승인 키까지 확장한다. 설치와 업데이트는 같은
    명령이며(멱등), 마커 불일치는 self-heal 한다(doctor `[16]`·`[17]`이 이미
    불일치를 표시한다).
  - **스코프 규칙**(검수 F9 — plan_conflict, 사람 판단으로 확정): 배열 설정이
    스코프 간 병합된다는 일반화는 **틀렸다**. 병합되는 것은 permission
    `allow`/`ask`/`deny`뿐이고, `enabledMcpjsonServers` 같은 일반 배열 설정은
    **가장 높은 우선순위 스코프가 통째로 override** 한다. → 설치기는 사용 중인
    최고 우선순위 스코프에 쓰거나, 더 좁은 스코프의 기존 정의를 **감지해
    보고**한다. 무시될 값을 조용히 기록하지 않는다.
  - **승인 정책**(사용자 지시, 2026-07-25): **설치기는 `permissions.ask`를
    생성하지 않는다.** exec 승인 강도는 호스트 권한 모드가 정한다.
    - 근거: `bypassPermissions`는 프롬프트와 안전 점검을 끄지만 **명시적 ask
      규칙은 이 모드에서도 프롬프트를 강제**한다. 규칙 평가는 deny → ask →
      allow 순이고 첫 매치가 결과를 정하므로 **더 구체적인 allow도 ask를 이기지
      못한다**. 실측에서 `ask` 2종과 `allow` 1종이 공존해 allow가 무력화된
      상태였다.
    - **이중 동의는 유지**한다: ① `--enable exec` 서버 프로필(기동 시) ② 호스트
      권한 모델(모드에 따름). D58의 "삼중 게이트" 중 호스트 ask 층은 **모드
      존중**으로 대체된다 — default 모드에서는 MCP 기본 프롬프트가 그대로
      작동하고, 사용자가 무프롬프트 모드를 명시적으로 선택한 경우에만 즉시
      실행된다.
    - exec 도구에 `_meta["anthropic/requiresUserInteraction"]`을 **붙이지
      않는다** — 붙이면 bypass에서도 프롬프트가 강제되어 위 정책과 모순된다.
    - doctor 호스트 스니펫을 ask 기반 문면에서 **모드 기반 안내**로 개정한다
      (D58에서 넣은 `permissions.ask` 예시가 대체 대상).
    - 강제 프롬프트를 원하는 사용자를 위해 `--exec-approval=ask`를 **opt-in**
      으로 제공한다. 기본값은 모드 존중이다.
    - **doctor 신설 진단**: ask 규칙이 allow를 가리는 조합을 감지해 보고한다.
      사용자가 스스로 알아채기 어려운 형태이며 실제로 발생했다.
  - **exec 활성화**는 명시 opt-in 플래그를 유지한다(기본 OFF, D58 계승).
  - **대상 환경**: 소유자 본인 머신들. 낯선 사용자를 위한 배포 채널은 비범위
    (§1.2).

- **D65** 툴체인 사용자 구성 격리 일반화:
  - **구조적 갭**: D59의 env allowlist는 닫힌 표로 잘 동작하지만, 그 표가
    통과시키는 `APPDATA`·`USERPROFILE`·`LOCALAPPDATA`(Windows)와 `HOME`(Unix)이
    **호스트 구성 파일로 가는 포인터**다. 즉 환경변수는 닫혔고 **파일 기반
    툴체인 구성은 열려 있다**. v0.11.1은 csharp 한 사례만 국소 차단했다.
  - **일반 규칙**: 러너별로 사용자 구성 파일 경로를 스크래치에 고정한다.
    - **go**: `GOENV`를 스크래치로 재지정(F11). 현재 `GOCACHE`·`GOPATH`·
      `GOTMPDIR`만 재지정하므로 호스트 go env 파일이 `GOFLAGS`·`GOPROXY`·
      `GOTOOLCHAIN`을 그대로 공급한다 — 빌드 동작과 재현성에 직접 영향한다.
    - **node/bun**: 사용자 npmrc 경로를 스크래치로 재지정.
    - **python**: user-site 비활성 + 구성 파일 경로 고정.
    - **pwsh**: `PSModulePath`를 인터프리터 자체 모듈 경로로 제한(F12). 현재
      호스트 값이 그대로 복사되어 호스트 설치 모듈이 자동 로드된다.
    - **csharp**: v0.11.1의 스크래치 `nuget.config` 유지.
  - **적용 실증 테스트**(v0.11.1 교차 검수가 노출한 갭): 구성 파일의 *생성*이
    아니라 **적용**을 검증한다. 러너 안에서 유효 설정을 조회해 호스트 값이
    보이지 않음을 확인하는 형태여야 한다 — 지금은 파일이 어떤 이유로든 무시돼도
    3-OS CI가 초록이다.
  - **쓰기 실패 계약**: 스크래치 구성 기록은 격리의 시행점이므로, best-effort로
    남길지 러너 오류로 올릴지를 러너 공통으로 정한다(v0.11.1은 경고만 남긴다).

- **D66** shell 방언·종료코드 계약:
  - **방언**: `language: "shell"`은 플랫폼 기본 셸이다 — Windows는 PowerShell
    (pwsh 7, 부재 시 Windows PowerShell 5.1 폴백), 그 외는 sh. v0.11.1에서
    스키마 문면에 표기했다. 정확한 인터프리터·버전은 응답 `runner` 필드가 준다.
  - **종료코드 계약 — (a) 현행 유지로 확정**(2026-07-25). shell 계열의
    `exit_code`는 **마지막 명령의 상태**이며 중간 비종결 오류를 대표하지
    않는다. 성공 판정은 `exit_code`와 `stderr`를 함께 보고 한다.
    - 이는 러너 결함이 아니라 **셸 일반의 정의된 동작**이다 — POSIX sh도
      `false; echo hi`가 0을 반환한다. PowerShell 고유 문제로 다루면 러너가
      언어별로 다르게 굴어 오히려 예측이 어려워진다.
    - **(b) 강제 기각**: `set -e` / `$ErrorActionPreference = 'Stop'` 주입은
      파이프라인·조건식·`|| true` 같은 정상 패턴을 깨뜨리는 함정이 많고,
      스니펫 선두 주입은 **오류 메시지의 행 번호를 어긋나게** 한다. 기본값이
      호출자의 정상 스니펫을 깨는 방향은 택하지 않는다.
    - **(c) 신호 필드 기각**: `stderr`가 응답에 온전히 오므로 판정 근거는 이미
      호출자에게 있다. 파생 필드는 매 호출 응답만 키운다.
    - 엄격 동작이 필요하면 **호출자가 스니펫 첫 줄에 직접 적는다**(`set -e`,
      `$ErrorActionPreference = 'Stop'`). 러너는 강제하지 않는다.
    - 계약 문면은 설계 문서와 doctor 안내에 둔다. 도구 스키마는 게이트 11 여유가
      86B뿐이라(§3) 문면 추가 대상이 아니며, 게이트 재기준화 시 후보로 남긴다.

- **D67** 저장 성장 운영 정책:
  - **신규 메커니즘이 아니다**(검수 F13). 회수 경로는 `purge --older-than
    --vacuum`(D50)으로 이미 존재하고 `--hook-only`는 항상 vacuum 한다. 임계
    104,857,600B는 `defaultContentFileWarnBytes` 기본값이며
    `CTR_CONTENT_FILE_WARN_BYTES`로 조정 가능한 **자문 값**이다.
  - **실측이 전제를 바꿨다**(2026-07-25, §3): free page는 전체의 **0.7%**
    (284 / 43,052 페이지)뿐이다. 즉 **회수할 여유 공간이 없어** VACUUM 단독은
    1.1MiB만 되돌린다 — 회수는 삭제가 선행되어야 의미가 있다. 또 **모든
    아티팩트가 7일 이내**(7일 초과 0건)라 `--older-than 7d`로는 아무것도 지워지지
    않는다. F13의 "회수 경로는 이미 있다"는 맞지만 회수할 대상이 없었다.
  - **성장 동인은 데이터가 아니라 인덱스다**: chunk 텍스트 36.0MiB에 파일이
    168.2MiB — porter·trigram 이중 FTS가 약 3.6배 승수를 만든다. 보존 정책은
    보관 기간을 줄일 뿐 이 승수를 없애지 못한다(§4로 이월).
  - **보존 정책 — 확정**:
    - **shadow 귀속 3일**, 기동 경로에서 자동 purge. 훅이 가로챈 출력은 대개
      해당 세션 안에서 소비되므로 짧게 잡는다.
    - **explicit 소스는 무기한 보존**. 사용자가 의도를 갖고 넣은 데이터이며
      `--hook-only`가 이미 이를 보호한다.
    - **자동 경로에서 VACUUM은 하지 않는다.** 삭제로 생긴 free page는 이후
      기록에 재사용되어 파일이 정상상태에서 멈춘다 — 목표는 파일 축소가 아니라
      **성장 억제**다. 기동 시 168MiB VACUUM은 지연이 크고 라이브 서버 제약도
      받는다.
    - **디스크 반환이 필요할 때만 수동**: 서버 비가동 시
      `purge --project <p> --older-than <dur> --vacuum`.
  - **실행 주기 — 확정**: 서버 **기동 시 1회**, 기존 SweepStale과 같은 지점.
    stdio 서버는 종료가 보장되지 않아 종료 훅은 신뢰할 수 없다.
  - **임계값**: 현재 104,857,600B는 상시 초과 상태라 신호로서 죽어 있다. 보존
    정책 적용 후 정상상태를 관측해 재설정한다 — 실측 성장률이 하루 약
    33–37MB이므로(§3) 기대 정상상태는 shadow 3일분 + explicit 누적이다. 관측
    전 임의 상향은 하지 않는다(자문 값의 신호 기능을 다시 죽이지 않기 위해).

## 1. v0.12 제품 계약

### 1.1 범위

## 2. 검증·테스트 계약

- **D63**: 네임스페이스 버킷팅·세션 노출 상태 기록의 단위 테스트. 상시 로드
  전후의 adoption 관측 기록(§3 형식). 상주 총량 측정은 등록 서버 합집합 기준.
- **D64**: 재실행 무변화(멱등) 테스트, 좁은 스코프 정의 감지 테스트, **설치
  결과에 `permissions.ask` 항목이 생성되지 않음**을 고정하는 테스트, 마커
  self-heal 테스트, ask-가림 진단의 단위 테스트.
- **D65**: 러너별 구성 적용 실증(3-OS CI). 호스트에 구성 파일이 존재하는 상황을
  픽스처로 만들어 스크래치 구성이 이긴다는 것을 확인한다.
- **D66**: 비종결 오류가 있는 스니펫이 `exit_code` 0과 비어 있지 않은 `stderr`를
  함께 반환함을 고정하는 테스트(계약 회귀 방지). 러너가 엄격 모드를 주입하지
  않는다는 것도 함께 고정한다.
- **D67**: 기동 시 자동 purge의 단위 테스트 — 3일 경계, shadow 한정, explicit
  보존, **VACUUM 미수행**. 성장 억제 효과는 정상상태 관측으로 확인한다(§3 형식).
