## 2. What was done

**Scripted cancellation smoke (`TestE2E_CallToolCancellation`, cmd/context-router/main_test.go,
PR #5 = 37e4d42 + 52e2942, merged b43f9be):**
- go-sdk `ClientSession`+`CommandTransport` spawns the real binary; ctx cancel at 1s makes
  the SDK auto-emit `notifications/cancelled` (transport.go `call()` ctx.Err branch returns
  `errors.Join(ctx.Err(), …)` → `errors.Is(err, context.Canceled)` matches).
- Final assertion design (evolved through review rounds):
  (a) prompt `context.Canceled` return — **client-side contract only** (jsonrpc2 `Await` is a
  local select; proves notification *sent*, not *processed*);
  (b) server-side processing observed **via worker-slot release**: occupy both workerSem
  slots (≤2) with long calls, cancel both, then run **two** trivial transforms concurrently —
  each must finish <7s (cancel processed ≈2s vs handler-timeout hold ≥9s; two probes because
  one probe passes if only one of two cancellations was processed — Codex P1+P2);
  (c) follow-up `ctr_search` + graceful exit code 0 on stdin close.
- Placement verdict (reviewer): resident E2E in main_test.go (regression guard; the "자동화
  금지" clause covers real-host registration only — session-03 precedent).

**Three root causes found & fixed along the way (all with hard evidence):**
1. **Windows worker nondeterministic early death** (session-03 recipe's 8MB-garbage churn):
   isolated at transform layer — 7/20 deaths 124ms–1.58s, `VirtualAlloc errno=1455` →
   Go runtime OOM abort (exit 2). GC commit-return lag lets commit hit the 256MB Job cap
   despite ~12MB live. Same family as PR #4's unexplained ubuntu 194ms death → **that
   mystery is now explained**. Fix: allocation-free count-scan workload (4MB base ×
   `count("xx")` ×8000; natural completion >10s anchored by real-host 1500-rep timeouts ×5.3).
2. **Ubuntu worker instant death (8.4ms) even with allocation-free workload** (PR #5 CI run
   29676082922): RLIMIT_AS caps *address space*, colliding with Go runtime VA reservations —
   linux-specific, script-independent. Fix: churn-pair retry ≤3 then linux skip
   (fail-closed known gap; windows stays hard-fail = regression signal); (b)-probes tolerate
   linux `worker killed` since **the discriminating signal is elapsed time, not success**.
3. **Test-side deadlock (CI 10m timeout, run 29676073834)**: goroutine dump pinned it —
   test's own `cmd.Wait()` raced the SDK read-loop's `cmd.Wait()` (via pipeRWC.Close);
   stderr-copier join signal is consumed once, loser blocks forever. The 49s vs 10m50s CI
   failures were the same race, opposite winners. Fix: `failDiag` helper — `sess.Close()`
   first (jsonrpc2 `updateInFlight` serializes the real close exactly once), then read stderr.

## 5. Standing protocols (delta only — rest as session-03 §5)

- **New lesson — never call `exec.Cmd.Wait()` on a process the go-sdk transport owns**: the
  SDK read-loop's close path calls it; concurrent Wait deadlocks on the io-copier join
  channel. Diagnostics must route through `sess.Close()` (serialized once by jsonrpc2).
- **New lesson — memory-cap asymmetry**: windows Job Object caps *commit* (allocation-heavy
  workloads die from GC lag), unix RLIMIT_AS caps *address space* (Go runtime VA reservations
  can kill a worker at spawn, script-independent). Any test asserting "worker survives N
  seconds" is unsound on linux; design assertions around time-based signals or tolerate
  fail-closed deaths.
- Codex wedge protocol unused this session (all passes finished naturally) — keep the
  10–12min cap + PowerShell cancel procedure as-is.
- **New technique — process-watcher adjudication**: when host-side behavior is opaque
  (did a signal reach the server?), observe the *child process table* instead: worker
  lifetimes vs a measured no-signal control give a deterministic verdict without host
  cooperation. Reusable for any spawn-based contract question.
