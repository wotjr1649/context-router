### 배운 것 — 다음 세션이 반복하지 말 것

1. **계획 리뷰가 스펙 리뷰보다 값이 높았다.** 계획은 구현자가 **축자로 따르는** 문서라, 잡힌
   것들이 그대로 결함으로 실현될 성질이었다 — 정상 파일을 동결시키는 코드, 컴파일이 깨지는
   태스크 경계, 물지 않는 유도 FAIL 둘.
2. **"유도 FAIL을 넣었다"와 "그 유도 FAIL이 문다"는 다르다.** v0.15는 게이트 11에서 이 부류를
   릴리스 뒤에 발견했고, 이번에는 계획 단계에서 둘을 잡았다. 감시선이 두 겹이면 **안쪽
   하드코딩이 바깥쪽 결함을 가린다** — 판정값을 두 곳에서 정하지 않는 것이 그 예방이다.
3. **역슬래시 개수를 grep 패턴으로 세지 마라.** 셸 인용 → ERE/PCRE 두 계층에서 리터럴 개수가
   갈리고 Bash PCRE는 `\u`를 거부한다. 같은 파일에서 "둘 패턴"과 "넷 패턴"이 같은 개수를 반환해
   오염으로 오판했다. **앞 문맥을 뽑아 세는 것**(`grep -oE '.{6}u0061' | sort | uniq -c`)이
   정확하고, 픽스처의 백슬래시와 검증 명령 문자열 안의 백슬래시도 그렇게 구별된다.
4. **가장 신뢰할 수 있는 검증은 그 코드를 돌리는 것이다.** 격리 모듈에 수정판과 초안을 함께 두고
   같은 픽스처로 돌리면 표기의 정확성과 감시선의 물림이 한 번에 실측된다.
5. **서브가 `plan_conflict`를 넓게 해석한다.** 구조 자문 서브가 9건을 `true`로 표시했지만 전부
   "계획 문면과 다르다"는 뜻이었고 확정 결정과 어긋나는 것은 없었다. 통합 서브에 재판정을
   지시해 0건으로 정정했다. **dispatch에 그 구별을 축자로 적어야 한다.**
6. **컨트롤러의 자체 검토도 근거가 틀릴 수 있다.** `codexVerdict.Anomaly`를 린터 위험으로
   판단했는데 실제 근거는 스펙 요구(`[20]`도 사유를 인쇄한다)였다. 수정은 옳았고 근거만 틀렸다.
7. **Codex는 이 호스트에서 `task --background`로 쓴다.** `review --base`는 git이 필요해
   구조적으로 불가능하다(§5.7 승계). `task`는 git 스코프를 아예 타지 않아 실패 경로가 하나
   줄고, 문서·계획 검수라는 목적에도 맞다. focus에 "셸을 쓰지 말고 파일을 읽어라"를 명시하고
   런처를 **파이프로 자르지 않고 파일로 리다이렉트**하면 두 번 다 성공했다.
